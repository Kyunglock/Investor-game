# 실제 뉴스 소재 (RAG) 설계

> 상태: 설계 (구현 전, 2026-10-27) · 결정 기록: [decisions.md](../../decisions.md) 101번
> 사용자: "투자 시뮬레이션 게임에 실제 종목이 들어가 대신에 가격은 기존대로 랜덤으로 할거고 대신에 급락, 급등할 때 뉴스소재는 진짜로 실제 있었던 뉴스를 보여줄 생각이야 미장은 빼고 국장만" → 이름은 "엔비디아 엑조디아 이런식으로 웃기게", "삼성전자는 그냥 삼송전자가 나은거같은데" → 뉴스 고르는 방식은 "A로 가자"(방향과 무관하게 고르고 양면으로 다시 쓰기).
> 목적: RAG(검색 증강 생성)를 직접 만들어 보는 실습이기도 하다. 그래서 어디에 RAG가 필요하고 어디에 필요 없는지를 먼저 가른다.
> 표기: **(확정)** = 사용자가 정한 것, **(추천 수용)** = 추천안을 사용자가 고른 것, **(제안)** = 확인받지 않은 초기안.

## 1. 결정한 것

| 항목 | 결정 |
|---|---|
| 뉴스 소재 | 뉴스 이벤트의 소재를 **실제로 있었던 국내 기업 뉴스**로 한다 (확정). 미국 종목은 뺀다 (확정) |
| 가격 | 지금처럼 **랜덤**(추세+잡음+충격)이다. 실제 주가 반응은 쓰지 않는다 (확정) |
| 종목 이름 | 지금보다 **더 크게, 웃기게** 바꾼다 (확정). 단 삼성 계열은 지금의 **"삼송"**을 유지한다 (확정). 이름표는 6절 |
| 뉴스 고르기 | **숨은 방향과 무관하게** 사건을 고르고, 본문은 **호재·악재가 섞이게 다시 쓴다** (추천 수용, "A"). 지금 구조(뉴스를 보고 고른 뒤 50:50 방향으로 움직임, [event.md](../../specs/event.md) 5.4절)를 그대로 지킨다 |
| RAG가 도는 곳 | **오프라인 콘텐츠 빌드**에서만 돈다. 게임 실행 중에는 검색도 LLM 호출도 없다 (제안, 2.3절) |

### 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 방향에 맞춰 고르기 (급락엔 악재, 급등엔 호재, "B") | 뉴스를 읽는 순간 정답이 보인다. 안목 힌트·줏대 판정이 무의미해진다 |
| 게임 중에 검색·생성 | 성인기 1년이 12초라 로컬 LLM을 기다릴 수 없다. 같은 시드에서 같은 판이 나와야 하는데([event.md](../../specs/event.md) 5.7절) 색인이 바뀌면 깨진다 |
| 실명 그대로 | 실존 기업 이름을 그대로 쓰는 부담. 지금도 패러디 이름을 쓴다 |

## 2. 왜 RAG인가

### 2.1 세 단계와 검색 조건

| 단계 | 하는 일 | 검색 조건이 | 방법 |
|---|---|---|---|
| 고르기 | 게임이 정한 종목·강도에 맞는 사건을 꺼낸다 | **값** (종목, 강도) | SQL. 라벨을 미리 붙여 두면 된다. RAG 아님 |
| 바꾸기 | 실제 기사를 게임 뉴스 형식(제목 + 양면 본문 4문장)으로 다시 쓴다 | **글** ("이 사건을 다룬 다른 기사, 반대 의견") | 벡터 검색으로 근거를 모으고 그 근거로만 생성. **RAG** |
| 잇기 | 연결 뉴스(갈래)로 그 사건의 후속 보도를 찾는다 | **글** ("이 기사의 다음 이야기") | 벡터 검색 + LLM 판정 |

- 조건이 값이면 SQL, 조건이 글이면 의미 검색이다. 고르기에 벡터를 쓰면 억지가 된다.
- 바꾸기가 RAG의 원래 목적과 맞는 이유: 실제 기사는 대개 한쪽 논조라 반대쪽 논점("다만 …")을 채워야 하는데, 근거 없이 시키면 LLM이 숫자·코멘트를 지어낸다. **실존 기업에 대해 지어내면 안 된다.** 같은 사건의 다른 기사·공시·반대 의견을 찾아 넣고 그 안에서만 쓰게 한다.
- 잇기가 의미 검색인 이유: "영업이익 급감 → 감산 효과 → D램 가격 반등"처럼 같은 이야기도 단어가 계속 바뀐다. 라벨(종목·호재/악재)로는 "그 이야기의 다음 편"을 못 찾는다.

### 2.2 같은 사건 묶기

사건 하나에 언론사별 기사가 수십 개 나온다. 묶지 않으면 한 판에 같은 사건이 표현만 바꿔 여러 번 나온다. 임베딩 유사도로 묶어 **사건** 단위로 다룬다 (RAG는 아니지만 같은 벡터 색인을 쓴다).

### 2.3 실행 시점

```
[오프라인 파이프라인]                                           [게임]
수집 → 라벨 → 청킹·임베딩 → 사건 묶기 → 카드 생성(RAG) → 치환 → 검사 → 사람 검수 → 내보내기
                    (pgvector)                                                 ↓
                                                     content/news-real.json → 콘텐츠 카탈로그 → 이벤트 운영
```

- 게임은 검수가 끝난 카드 파일만 읽는다. pgvector도 LLM도 모른다 (제안).
- 카드 파일은 커밋되는 콘텐츠라 판 재현성(같은 시드 = 같은 판)이 유지된다.

## 3. 파이프라인 구성

| 항목 | 제안 | 비고 |
|---|---|---|
| 위치 | 이 저장소 `tools/news-rag/` | 게임 서버·웹과 따로 빌드한다. 게임 CI에 넣지 않는다 |
| 언어 | Python | 본문 추출·임베딩·LLM 클라이언트가 가볍다. kwak-service collector의 본문 보강 관례(본문 상태값, 최소 길이)를 옮겨 쓸 수 있다. Java(Spring AI의 pgvector 저장소)도 가능 (미결정 1) |
| DB | `compose.yaml`에 **별도 서비스** `newsrag-db` (`pgvector/pgvector:pg17`, 포트 5433, 프로필 `rag`) | 게임 DB(`investor`)와 섞지 않는다. 평소 `docker compose up`에는 뜨지 않는다 |
| 생성 LLM | kwakai(vLLM, OpenAI 호환, gemma4-31b) | 라벨·요약·카드 생성·검사 판정 |
| 임베딩 | bge-m3 (다국어, 1024차원) | kwakai 서버에 함께 띄울 수 있는지 확인 필요. 안 되면 CPU 배치로도 수천 건은 돈다 (미결정 3) |

각 단계는 **멱등**하게 상태값을 둔다(다시 돌려도 끝난 건 건너뛴다).

## 4. 데이터

### 4.1 소스

| 소스 | 쓰는 곳 | 비고 |
|---|---|---|
| DART 공시 (OpenAPI) | 사건의 뼈대 (잠정실적, 단일판매·공급계약, 유상증자, 소송 등) | 날짜·사실이 정확하다. API 키 필요 |
| 뉴스 기사 | 맥락, 시장 해석, 반대 의견 | 검색 API로 목록, 원문에서 본문 추출. **약관 확인 필요** (미결정 2) |

- 원문 본문은 **파이프라인 DB에만** 둔다. 저장소에 커밋하지 않고 게임에 내보내지 않는다.
- 첫 범위: 반도체 세 종목(삼송전자, SK하이킥스, 한밤반도체), 최근 2년 (제안).

### 4.2 스키마 (`newsrag-db`)

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- 수집한 문서. 원문은 여기에만
CREATE TABLE rag_document (
  id            bigserial PRIMARY KEY,
  source        text NOT NULL,              -- DART, NEWS
  stock_code    text NOT NULL,              -- 실제 종목코드 (005930)
  publisher     text,
  published_at  timestamptz NOT NULL,
  title         text NOT NULL,
  url           text NOT NULL UNIQUE,
  body          text,
  status        text NOT NULL DEFAULT 'COLLECTED'  -- COLLECTED, LABELED, EMBEDDED, SKIPPED
);

-- LLM 라벨. 고르기(SQL)와 근거 검색 필터에 쓴다
CREATE TABLE rag_label (
  document_id   bigint PRIMARY KEY REFERENCES rag_document(id),
  tone          text NOT NULL,              -- POS, NEG, MIXED, NEUTRAL
  impact        smallint NOT NULL,          -- 1~5
  topic         text NOT NULL,              -- EARNINGS, CONTRACT, REGULATION, TRIAL, LAWSUIT, INDUSTRY, ...
  is_event      boolean NOT NULL,           -- 단순 시황·주가 기사는 false
  model         text NOT NULL
);

-- 검색 단위
CREATE TABLE rag_chunk (
  id            bigserial PRIMARY KEY,
  document_id   bigint NOT NULL REFERENCES rag_document(id),
  seq           smallint NOT NULL,
  text          text NOT NULL,
  embedding     vector(1024) NOT NULL,
  UNIQUE (document_id, seq)
);
CREATE INDEX ON rag_chunk USING hnsw (embedding vector_cosine_ops);

-- 사건 = 같은 일을 다룬 문서 묶음
CREATE TABLE rag_event (
  id            bigserial PRIMARY KEY,
  stock_code    text NOT NULL,
  occurred_on   date NOT NULL,
  summary       text NOT NULL,
  centroid      vector(1024) NOT NULL,
  impact        smallint NOT NULL,
  topic         text NOT NULL
);
CREATE TABLE rag_event_member (
  event_id      bigint REFERENCES rag_event(id),
  document_id   bigint REFERENCES rag_document(id),
  PRIMARY KEY (event_id, document_id)
);

-- 생성한 게임 뉴스 카드
CREATE TABLE rag_card (
  id            bigserial PRIMARY KEY,
  event_id      bigint NOT NULL REFERENCES rag_event(id),
  title         text NOT NULL,
  body          text NOT NULL,
  evidence      jsonb NOT NULL,             -- 문장 번호 → 근거 chunk id 목록
  checks        jsonb NOT NULL,             -- 7절 자동 검사 결과
  status        text NOT NULL               -- DRAFT, REJECTED, APPROVED, UNSUITABLE
);

-- 연결 뉴스 후보
CREATE TABLE rag_followup (
  parent_event_id bigint REFERENCES rag_event(id),
  child_event_id  bigint REFERENCES rag_event(id),
  similarity      real NOT NULL,
  gap_days        integer NOT NULL,
  relation        text,                     -- ESCALATE(악화), RESOLVE(해소), CONTINUE(진행). LLM 판정
  accepted        boolean,
  PRIMARY KEY (parent_event_id, child_event_id)
);
```

## 5. 단계별 규칙

### 5.1 라벨

LLM에 기사 제목·본문 앞부분을 주고 JSON으로 `tone`, `impact`, `topic`, `is_event`를 받는다. `is_event=false`(시황 정리, 주가 등락만 다룬 기사)는 사건 후보에서 빠지지만 근거 검색에는 남는다.

### 5.2 청킹·임베딩

- 뉴스: 문단을 이어 붙여 300~500토큰 단위. 짧은 기사는 통째로 하나 (제안).
- 공시: 섹션(표제) 단위로 자르고, 표는 행을 문장으로 풀어 쓴다 (제안).
- 청크 앞에 `[종목명 · 날짜 · 제목]` 머리말을 붙여 임베딩한다. 짧은 문단이 어느 기사 것인지 잃지 않게 한다.

### 5.3 사건 묶기

- 같은 종목, 발행일 차이 3일 이내, 대표 임베딩(제목+첫 문단) 코사인 유사도 0.82 이상이면 같은 사건 (초기값, 조정).
- 공시가 있으면 공시 날짜를 사건일로 한다. 요약은 LLM, `impact`는 구성 문서의 최댓값.

### 5.4 카드 생성 (RAG)

1. **검색어**: 사건 요약의 임베딩.
2. **필터**: 같은 종목, 날짜 `[사건일 − 3일, 사건일 + 14일]`.
3. **양쪽을 따로 검색**: `tone ∈ {POS, MIXED}`에서 상위 4개, `tone ∈ {NEG, MIXED}`에서 상위 4개. 한쪽만 모으면 양면 본문을 쓸 수 없다.
4. **업황 보강**: 같은 섹터(종목 필터 대신 섹터) 청크 상위 2개.
5. 한쪽 근거가 0개면 섹터 범위로 넓혀 다시 찾고, 그래도 없으면 `UNSUITABLE`로 둔다. 횡령·상장폐지처럼 양면이 성립하지 않는 사건은 이 게임에 맞지 않는다.
6. **생성 규칙** (프롬프트):
   - 근거에 있는 사실만 쓴다. 문장마다 근거 번호를 단다.
   - 제목 1줄 + 본문 4문장: 사건 1 · 호재 쪽 1 · 악재 쪽 1 · 불확실성 1. 지금 `news.json` 본문과 같은 결.
   - **주가 반응을 쓰지 않는다**(○% 올랐다, 상한가, 급락 등). 게임 가격은 랜덤이다.
   - **연도·날짜를 쓰지 않는다.** 게임 시간은 나이로 흐른다.
   - 인물은 이름 대신 **직함**(회장, CEO)으로 쓴다.
   - 이 단계에서는 실명 그대로 쓴다. 이름 바꾸기는 다음 단계에서 코드로 한다.

### 5.5 이름 바꾸기 (치환)

- 6절 사전으로 **긴 이름부터** 바꾼다(SK하이닉스를 SK보다 먼저). LLM에 맡기지 않는다. 문장마다 들쭉날쭉해지기 때문이다.
- **조사를 맞춘다.** 받침이 바뀌는 이름이 있다(마이크론은 → 마이크로웨이브는). 셀트리온 → 셀프트리온처럼 받침이 같으면 그대로 둔다. 웹의 `spouseTerms.ts`(91번)와 같은 방식으로 뒤 조사를 고친다.
- 사전에 없는 고유명사가 남는지는 7절 검사가 잡는다.

### 5.6 연결 뉴스 (잇기)

1. 승인된 카드의 사건 E마다, 같은 종목(또는 업황 사건이면 같은 섹터)에서 E보다 30~540일 뒤의 사건을 후보로 한다.
2. 중심 벡터 코사인 유사도 상위 5개를 고른다.
3. LLM이 "후보가 E 이야기의 다음 편인가, 관계는 악화·해소·진행 중 무엇인가"를 판정한다. 통과한 것만 `rag_followup.accepted = true`.
4. 콘텐츠의 `followups`로 내보낸다: `on: ["*"]`, `directionRule: FREE`, `delayDays`는 실제 간격을 `[30, 365]`로 자른 값 (제안). 행동에 따른 갈래는 미결정 5.

- 이름(`삼송전자` 외)은 제안이고 바꿀 수 있다.

### 6.2 뉴스에 함께 나오는 이름

| 실제 | 바꿀 이름 |
|---|---|
| 삼성(그룹) | 삼송(그룹) |
| 엔비디아 | 엑조디아 (확정) |
| TSMC | TMI반도체 |
| 애플 | 파인애플 |
| 마이크론 | 마이크로웨이브 |
| 인텔 | 인절미텔 |
| 테슬라 | 테스형 |

수집하며 자주 나오는 고유명사(제품명·계열사·경쟁사)를 이 표에 더한다. 첫 범위에서 빈도 상위 30개를 뽑아 채운다 (제안).

### 6.3 이름 규칙

- 원래 이름이 소리로 떠오르되 한 번 비튼다.
- **같은 그룹은 같은 접두사** (삼송전자·삼송바이오·삼송화재). 뉴스에 계열사 관계가 자주 나온다.
- **인물은 직함으로** 쓴다. 실존 인물 이름은 패러디하지 않는다 (제안).
- **비하로 읽히는 이름은 피한다.** 실존 기업에 부정적인 사실을 암시하는 이름(예: 엔딩소프트)은 쓰지 않는다 (제안).

## 7. 자동 검사

카드 하나에 모두 통과해야 사람 검수로 넘어간다.

| 검사 | 방법 | 실패하면 |
|---|---|---|
| 근거 | 문장마다 근거 번호가 있는지 + LLM 판정("인용한 청크가 이 문장을 뒷받침하는가") | 다시 생성 (2번까지), 그래도 실패면 `REJECTED` |
| **방향 누출** | 카드만 보여 주고 "이 뉴스 뒤 주가는 오를까 내릴까, 확신도 0~100"을 묻는다. 확신도 70 이상이면 실패 (초기값) | 다시 생성 |
| 실명 누출 | 실명 목록(6절의 실제 이름 + 수집 중 쌓은 인물·제품명) 문자열 검사 | `REJECTED` |
| 금지 표현 | 정규식: `%`, 상한가, 하한가, 급등, 급락, 주가, `\d{4}년`, `\d+월 \d+일` | 다시 생성 |
| 형식 | 제목 30자 이내, 본문 4문장 | 다시 생성 |

- 방향 누출은 카드 묶음 전체로도 본다. 판정 LLM이 실제 라벨(호재·악재) 쪽을 맞힌 비율이 **50%에 가까워야** 한다. 크게 벗어나면 생성 프롬프트를 고친다.
- 검사 결과는 `rag_card.checks`에 남겨 검수 화면(또는 리포트)에서 본다.

## 8. 게임 쪽 변경 (작게)

| 변경 | 내용 |
|---|---|
| 카드 파일 | `content/news-real.json`: 파이프라인이 만든다. **손으로 고치지 않는다.** 지금 뉴스 정의 형식([event.md](../../specs/event.md) 6절)에 필드 셋을 더한다 |
| `stock` | 대상 종목 코드 고정. 있으면 섹터에서 종목을 뽑지 않는다. 난수 순서(정의 → 종목 → 방향 …)를 지키려고 **종목 난수는 뽑되 버린다** (제안, 94번과 같은 시드 순서 유지 원칙) |
| `origin` | `REAL`. 창작 뉴스는 없음(= `AUTHORED`) |
| `sources` | `[{ publisher, publishedOn, url }]`. 검수·출처 기록용. API에 내릴지는 미결정 4 |
| 강도 | `impact`를 `magnitude`로: 1~2 → 600~1500bp, 3 → 1000~2200bp, 4~5 → 1500~3000bp (제안). 방향은 항상 `FREE` 5000 |
| 범위 | `topic`이 REGULATION·INDUSTRY면 `sectorWide: true` (제안) |
| 섞는 비율 | 창작 뉴스와 실제 뉴스를 함께 쓴다. `event.news.real-weight-percent`(초기값 100 = 같은 가중치) (제안) |
| 종목 이름 | `stocks.json`의 `name`을 6.1절대로 |
| 안내 | 게임 시작 또는 뉴스 카드에 "실제 사건을 각색했고, 가격 움직임은 실제와 관계없습니다" 한 줄 (제안) |

콘텐츠 카탈로그(`JsonContentCatalog`)가 `news.json`과 `news-real.json`을 함께 읽고, `followups.definition` 존재·순환 검사를 두 파일에 걸쳐 한다.

## 11. 위험 (확인 필요)

아래는 판단이 아니라 확인할 목록이다. 공개 배포 전에 확인한다.

- **기사 저작권**: 원문을 싣지 않고 다시 쓴 문장만 낸다. 그래도 각색 범위가 충분한지는 확인이 필요하다.
- **뉴스 API 약관**: 본문 저장·가공이 허용되는지.
- **실존 기업 각색**: 이름을 바꿔도 실제 사건과 숫자로 어느 회사인지 알아볼 수 있다. 그래서 근거 검사(7절)가 있다.
- **오해**: 실제 뉴스 + 랜덤 가격이 실제 주가 반응처럼 읽히지 않게 안내한다.
