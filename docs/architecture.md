# 아키텍처 설계

> 상태: 초안 v0.2 (서버 주도 구조로 전면 개정)
> 표기: **(확정)** = 대화에서 정해진 것, **(제안)** = 제 판단이며 아직 합의되지 않은 것. 요구사항은 [prd.md](./prd.md), 게임 수식은 [poc.md](./poc.md)를 따른다.

## 1. 전제

| 항목 | 내용 |
|---|---|
| 플랫폼 | 반응형 웹 + PWA (확정). PWA는 홈 화면 추가와 화면 자산 캐시 용도이며 오프라인 플레이는 지원하지 않는다 |
| 온라인 | **온라인 전용** (확정). 네트워크가 끊기면 게임이 진행되지 않는다 |
| 계산 주체 | 서버가 **능력치, 이벤트 선택에 따른 확률 계산(판정, 힌트), 자산, 이벤트 운영**을 맡는다 (확정) |
| 시간 진행 | **클라이언트가 맡는다** (확정). 시계, 나이 표시, 일시정지, 배속은 클라이언트에서 처리하고 서버에는 현재 게임 시각을 알린다 |
| 클라이언트 역할 | 화면 표시, 입력 전달, 시계 구동. 능력치·확률·숨은 값 등 규칙 정보를 알지 못한다 (확정) |
| 진행 상태 | 서버에 저장한다. 능력치 포함 (확정) |
| 계정 | 없음. 익명 세션으로 진행 중인 판과 결과를 묶는다 (확정) |
| 콘텐츠 | 직접 작성한 이벤트 풀(뉴스 등)을 서버가 소유하고 사용한다. 자동 생성은 하지 않는다 (확정) |
| 결과 저장 | 판이 끝나면 결과를 저장한다. 활용 방안은 나중에 정한다 (확정) |
| 랭킹 | 하지 않는다 (확정) |
| 한 판 | 실시간, 약 10분, 나이로 종료 (확정) |
| 작업 방식 | 도메인별 에이전트가 Orca에서 병렬로 작업 (확정) |

서버 계산의 효과: 능력치, 뉴스의 숨은 방향, 판정 확률이 클라이언트에 노출되지 않는다. 규칙이 서버 한 곳에만 있어 두 벌을 유지할 필요가 없다.

시간을 클라이언트에 두는 이유: 시계는 화면 연출과 한 몸이라 지연 없이 부드러워야 하고, 연결 상태와 상관없이 일시정지·배속이 즉시 동작한다. 랭킹이 없어서 클라이언트가 시간을 조작해도 얻는 이득이 거의 없다.

### 2.1 DB 규칙 (확정)

- **외래 키(FK)를 쓰지 않는다.** 테이블 사이의 연결은 ID 값으로만 두고, 정합성은 애플리케이션이 지킨다. 인덱스와 유니크 제약은 사용한다.
- **Flyway 방식의 마이그레이션.** 손으로 쓴 버전 SQL 파일(`V<번호>__<설명>.sql`)을 순서대로 적용한다. 이미 적용된 파일은 수정하지 않고, 변경은 새 버전을 추가한다.
- **DB 스키마는 하나만 쓴다.** MSA로 분리하는 것은 목표가 아니다 (확정).

구체안(제안):

- 도메인은 **테이블 이름 접두사**로 자기 테이블을 구분한다. 예: `asset_account`, `event_instance`. 접두사는 도메인 이름과 같다.
- 다른 도메인의 테이블을 읽거나 조인하지 않고, 필요하면 해당 도메인의 서비스 인터페이스를 호출한다. 스키마로 막을 수 없으므로 코드 규칙(ArchUnit)과 리뷰로 지킨다. 한 스키마라고 해서 이 규칙을 느슨하게 할지는 미결정이다.
- Flyway 위치는 `db/migration` 하나다. 파일 이름에 도메인을 넣는다. 예: `V202610171030__asset_init.sql`.
- 버전 번호는 시각 기반(`yyyyMMddHHmm`)으로 쓰고, CI가 번호 중복을 검사한다. 에이전트들이 병렬로 마이그레이션을 추가해도 같은 번호를 쓰지 않게 하려는 장치다.
- 병합 순서가 번호 순서와 어긋날 수 있어서 개발과 CI 환경은 Flyway의 `outOfOrder`를 켠다. 운영 환경은 통합 담당이 병합 순서를 관리한다 (미결정).
- JPA의 연관 관계 매핑과 스키마 자동 생성은 쓰지 않는다.

## 3. 서버 도메인 구조 (제안)

모듈형 모놀리스로 시작한다. 한 프로젝트 안에서 패키지를 도메인별로 나누고, 도메인 경계를 어기면 빌드가 실패하게 한다. MSA 분리는 목표가 아니다 (확정). 다음 규칙을 지킨다.

1. 도메인은 자기 데이터를 단독 소유하고, 다른 도메인은 서비스 인터페이스로만 접근한다.
2. 도메인은 테이블 이름 접두사로 구분한다 (2.1절).
3. 도메인 사이는 ID로만 연결한다. FK는 없고, 다른 도메인의 테이블을 직접 조인하지 않는다.

### 도메인 목록

**게임 규칙 도메인** (분리하더라도 "게임" 서비스 하나로 묶는 것을 추천한다. 한 번의 선택이 여러 도메인을 연쇄 호출하므로 서비스 간 통신으로 풀면 느려진다.)

| 도메인 | 소유하는 상태 | 책임 |
|---|---|---|
| 캐릭터 | 능력치, 성장 | 랜덤 생성, 성장 규칙 |
| 자산 | 현금, 보유, 월급 | 매수·매도 처리, 손익, 주가 변동 |
| 이벤트 운영 | 이벤트 큐, 노출 이력 | 이벤트 생성 시점·노출 비중(관심 섹터), 스킵 규칙, 콘텐츠 선택 |
| 행동 | 없음 (순수 규칙) | 선택이 뒤집히는 판정(줏대 → 인내심/용기), 안목 힌트 생성 |
| 진행 | 마지막으로 보고된 게임 시각, 단계, 판 시드 | 단계 전환 규칙(저축 → 투자 시작), 시각 보고 검증(역행 금지, 한 번에 건너뛸 수 있는 최대 구간), 종료 판정과 결과 확정. 시계 자체는 클라이언트 몫 |

**플랫폼 도메인**

| 도메인 | 소유하는 상태 | 책임 |
|---|---|---|
| 세션 | 익명 세션 | 세션 발급과 확인 |
| 콘텐츠 | 이벤트 풀, 콘텐츠 버전 | 직접 작성한 이벤트 데이터 로드와 조회 |
| 결과 | 판 결과 기록 | 판 종료 시 결과 저장 |

**클라이언트 앱**은 도메인이 아니라 서버 API를 그리는 표현 계층이다 (7절).

### 호출 방향

```
API 계층 → 진행 → 이벤트 운영 → 콘텐츠
              ├→ 행동 → 캐릭터 (능력치 읽기)
              ├→ 캐릭터
              └→ 자산
진행 → 결과 (판 종료 시)
모든 요청 → 세션 (확인)
```

- 진행이 한 판의 조율을 맡는다.
- 행동은 상태가 없다. 캐릭터의 능력치와 난수 생성기를 받아 결과를 돌려주는 순수 로직이다.
- 하위 도메인은 상위 도메인을 호출하지 않는다.

## 4. 실시간 시간 흐름 (제안)

클라이언트가 시계를 쥐고, 서버는 시계가 앞으로 갈 때마다 그 구간의 결과를 계산한다.

- 클라이언트가 게임 시계를 구동한다. 약 10분 동안 나이가 오르고, 일시정지와 배속도 클라이언트가 처리한다.
- 게임 시각이 일정 구간(예: 게임 속 1개월 또는 몇 초)만큼 흐르면 클라이언트가 서버에 **"여기까지 시간이 흘렀다"** 고 보고한다.
- 서버는 그 구간에 대해 월급 입금, 주가 변동에 따른 손익, 발생한 이벤트를 계산해서 응답에 담는다.
- 선택형 이벤트(뉴스, 직업 선택)가 응답에 오면 클라이언트는 시계를 멈추고 사용자의 선택을 기다린다. 선택은 서버로 보내 판정을 받는다. 알림성 이벤트는 시계를 멈추지 않으며 스킵할 수 있다.
- 서버는 보고된 시각이 **거꾸로 가지 않는지**, **한 번에 건너뛰는 구간이 상한을 넘지 않는지** 확인한다. 클라이언트가 이벤트를 건너뛰며 시간만 앞당기는 것을 막는 장치다.
- 연결이 끊기면 클라이언트는 시계를 멈추고 재연결을 기다린다. 서버는 시각 보고를 받을 때만 계산하므로 "끊긴 동안 서버에서 시간이 흐르는" 문제가 없다.
- 난수는 판마다 서버가 시드를 만들어 쓴다. 같은 시드와 같은 보고·선택 순서면 같은 판이 재현되어 버그 재현과 밸런스 검증에 쓴다.
- 서버의 시간 관련 로직은 현재 시각을 직접 읽지 않고 보고된 값으로만 계산하므로 테스트에서 임의의 시각 열로 검증할 수 있다.

## 5. API 개요

모든 경로는 `/api`로 시작한다. 계약의 원본은 `contracts/openapi/game.yaml`이다.

| 용도 | 요청 | 상태 |
|---|---|---|
| 세션 확보 (없으면 발급, `IG_SESSION` 쿠키) | `POST /api/sessions` | 구현됨 (워킹 스켈레톤) |
| 판 시작 (진행 중인 판이 있으면 버리고 새로 시작) | `POST /api/games` | 구현됨 |
| 진행 중인 판 조회 (재접속 시 이어하기) | `GET /api/games/current` | 구현됨. 세션당 판이 하나라 ID 대신 `current`를 쓴다 |
| 시간 경과 보고 | `POST /api/games/{id}/advance` | 구현됨. 월급 입금, 다음 이벤트 생성, 종료 처리. 응답의 `nextEventDay`까지만 클라이언트가 시계를 보낸다 |
| 선택 제출 | `POST /api/games/{id}/events/{eventId}/choose` | 구현됨. 뉴스는 판정 → 매매 → 주가 변동 → 성장을 거친 결과를 돌려준다 |
| 이벤트 스킵 | `POST /api/games/{id}/events/{eventId}/skip` | 예정 |
| 결과 조회 | `GET /api/games/{id}/result` | 예정 |

- 클라이언트에는 확률, 숨은 방향 등 규칙 정보가 내려가지 않는다. 응답에는 화면에 필요한 값(힌트 문구, 결과, 실제 행동과 원인 문구)만 담는다.
- 상세 명세는 OpenAPI로 작성하고 도메인별로 나눈다.

### 6.1 서버 패키지 규칙 (확정)

도메인 하나는 다음 구조를 가진다.

```
investorgame/asset/
  AssetService.java        공개 인터페이스. 다른 도메인이 호출하는 유일한 입구
  Trade.java ...           공개 입력·출력 record
  internal/                구현, 저장소, 행 매핑. 다른 도메인이 import하면 빌드 실패
```

- **도메인 우선으로 나눈다.** `controller/service/repository` 같은 계층 폴더로 나누지 않는다. 에이전트가 자기 도메인 폴더 하나만 보면 되고, 권한 경로를 `asset/**` 하나로 쓸 수 있다.
- **`common`에는 두 도메인 이상이 실제로 쓰는 코드만 둔다.** "쓸 것 같다"는 이유로 넣지 않는다. 도메인 규칙과 게임 수치는 넣지 않는다.
- **`common`, `config`, `architecture` 테스트는 통합 담당이 소유한다.** 에이전트는 추가가 필요하면 PR 댓글로 요청한다.

## 7. 클라이언트 구조 (제안)

- `web`은 게임 시계를 구동하고, 시간이 흐를 때 서버 API를 호출해 응답으로 화면을 그린다.
- 게임 규칙, 확률, 숨은 값을 클라이언트 코드에 두지 않는다. 클라이언트가 아는 것은 시계와 화면 표시뿐이다.
- 화면 문구는 클라이언트가 만들고(`labels.ts`, `log.ts`), 사실(숫자, 코드, 순서)은 서버가 준다. 인생 기록은 서버 `Game.log`의 코드·숫자를 클라이언트가 문장으로 바꾼다 (ui-redesign 설계 5.5절, 6절).
- OpenAPI에서 생성한 타입과 API 클라이언트를 쓴다.
- 새로고침이나 재접속 시 세션 쿠키로 `GET /api/games/current`를 호출해 서버의 현재 상태에서 이어한다. **재접속하면 일시정지 상태로 이어하고, 사용자가 "계속"을 눌러야 시계가 흐른다** (워킹 스켈레톤에서 정함). 새로 태어날 때는 바로 흐른다.
- 네트워크 오류 시 "연결이 끊어졌습니다" 화면을 보여 주고 재연결을 시도한다.

## 8. 에이전트 분업 (Orca)

Orca는 AI 에이전트 도구이며, 도메인별로 권한을 나눠 병렬 작업에 쓴다. 권한 단위(경로, 브랜치, 도구)는 아직 확인되지 않았다. 아래는 일반 원칙에 맞춘 제안이다.

**구현 에이전트는 5개로 시작한다 (확정).** 서버는 도메인 단위로, 클라이언트는 물리적 경계로 나눈다. 게임 규칙 도메인 5개는 "같이 바뀌는 것끼리" 세 갈래로 나눈다. 각 에이전트는 **Agent ID(`agent1`~`agent5`)** 를 가지며 권한은 이 ID에 매핑한다. 각 에이전트는 자기 도메인의 코드와 **그 도메인에 속한 DB 테이블, 그 테이블을 만드는 마이그레이션 파일**을 소유한다.

| Agent ID | 이름 | 도메인 | 소유 테이블 (접두사) | 소유 경로 | 읽기 전용 |
|---|---|---|---|---|---|
| `agent1` | 판정 | 캐릭터, 행동 | `character_*` | `backend/.../character/**`, `behavior/**`, 마이그레이션 `*__character_*.sql` | `contracts` |
| `agent2` | 시장·이벤트 | 자산, 이벤트 운영 | `asset_*`, `event_*` | `backend/.../asset/**`, `event/**`, 마이그레이션 `*__asset_*.sql`, `*__event_*.sql` | `contracts` |
| `agent3` | 플랫폼 | 세션, 콘텐츠, 결과 | `session_*`, `content_*`, `result_*` | `backend/.../session/**`, `content/**`, `result/**`, 마이그레이션 `*__session_*.sql`, `*__content_*.sql`, `*__result_*.sql`, 저장소 `content/` | `contracts` |
| `agent4` | 클라이언트 | (도메인 아님) | 없음 | `frontend/**` (E2E는 `frontend/e2e/`) | `contracts` |
| `agent5` | 진행 | 진행 | `progress_*` | `backend/.../progress/**`, `api/**`, 마이그레이션 `*__progress_*.sql` | `contracts` |

- 테스트 경로(`src/test/.../<도메인>`)는 해당 도메인의 소유 경로에 포함한다.
- **진행(agent5)** 은 다른 도메인을 엮는 조율 역할이라 인터페이스가 나오기 전에는 목(mock)으로 먼저 시작하고, 2단계에서 실제 도메인과 통합한다.
- 테이블 소유권은 접두사로 판정한다. 마이그레이션 파일 이름의 도메인과 만들려는 테이블의 접두사가 다르면 CI가 실패한다 (db.md 6절).
- 도메인 에이전트는 다른 도메인의 테이블을 읽거나 조인하지 않는다. 필요하면 서비스 인터페이스를 호출한다.

두 갈래 사이의 접점은 `contracts`에 먼저 확정한다.

| 접점 | 정해야 하는 것 |
|---|---|
| 이벤트 → 행동 | 판정에 넘기는 이벤트 값의 타입 (숨은 방향, 변동 폭, 줏대용 다른 뉴스의 분위기) |
| 행동 → 자산 | 판정 결과인 실제 행동과 이탈 원인의 타입 |
| 진행 ↔ 모든 도메인 | 각 도메인이 진행에 내놓는 인터페이스 |

**지원 역할** (구현 에이전트와 별도)

| 역할 | 수정 가능 | 책임 |
|---|---|---|
| 통합 (사람 또는 메인 에이전트) | `contracts`, 빌드 설정, 의존성, `backend/.../common`, `config`, `architecture` 테스트 | API 계약 관리, 공용 코드 관리, 병합, 충돌 해결 |
| 리뷰 | 없음 (지적만) | 스타일 위반, 중복, 도메인 경계 위반, 불필요한 추상화 지적 |
| 문서 | `docs/` | PRD, 스펙, 아키텍처 갱신 |

배분 이유와 확장:

- 이벤트 콘텐츠 작성은 상대적으로 가벼운 플랫폼 에이전트에 둬서 일을 고르게 나눈다.
- 도메인 경계는 에이전트 수와 무관하게 빌드에서 강제한다 (ArchUnit 또는 Spring Modulith). 한 에이전트가 여러 도메인을 맡아도 도메인 사이의 직접 호출은 실패한다.
- 각 에이전트가 맡은 범위 안에서는 의존이 없는 도메인부터 구현한다.

운영 규칙:

1. **계약이 먼저.** `contracts`(OpenAPI)와 도메인 사이의 서비스 인터페이스가 확정되기 전에는 병렬 작업을 시작하지 않는다.
2. **에이전트당 브랜치(또는 워크트리) 하나.** 병합은 통합 담당이 한다.
3. **계약 변경은 통합 담당에게 요청한다.** 다른 에이전트가 직접 고치지 않는다.
4. **병합 조건:** 테스트 통과, 리뷰 통과, 코드 스타일 준수, 도메인 경계 검사 통과.
5. 의존성 추가와 설정 변경은 통합 담당만 한다.
6. 에이전트는 자기 범위 밖의 코드와 테이블(접두사)을 수정하지 않는다. 마이그레이션 파일은 자기 도메인 이름이 들어간 것만 추가한다.
7. 각 에이전트는 자기 범위의 테스트를 직접 작성한다. 별도 QA 에이전트는 두지 않는다 (확정 구성이 3개이므로).

단계:

1. **0단계(직렬):** 아키텍처, 코드 스타일, 스펙, 계약 확정
2. **1단계(병렬):** agent1~agent5가 동시에 작업. 클라이언트(agent4)는 OpenAPI 목 서버로, 진행(agent5)은 도메인 인터페이스 목으로 진행
3. **2단계(직렬):** 진행(agent5)이 실제 도메인과 통합
4. **3단계(직렬):** 전체 통합, 체감 테스트, 수치 조정

## 9. 코드 슬롭 방지 (제안)

- 코드 스타일 문서를 에이전트 공통 지침으로 둔다 (다음 문서 작업).
- 리뷰 에이전트를 병합 전 관문으로 둔다.
- 규칙 예: 요청되지 않은 추상화 금지, 데이터로 풀 수 있으면 코드로 분기하지 않기, 한 번만 쓰는 헬퍼 금지, 주석은 이유만 쓰기.
- 도메인 용어집을 만들어 같은 개념에 이름이 여러 개 붙지 않게 한다 (예: 이탈/뒤집힘, 관망/보유).
- 코드 슬롭 방지용 스킬은 코드 스타일이 정해진 뒤에 만든다. 스타일 규칙이 곧 스킬의 내용이 된다.

## 10. 테스트 전략 (제안)

| 대상 | 방법 |
|---|---|
| 판정 확률 | JUnit에서 시드를 고정하고 대량 반복해 기대 확률과 비교 (poc.md 9절 방식) |
| 힌트 정답률 | 안목별 정답률 검증 |
| 시간 경과 계산 | 보고되는 게임 시각 열을 주고 월급·손익·이벤트 발생·종료 검증. 시각 역행과 과도한 건너뛰기 거부 검증 |
| 시계 (클라이언트) | Vitest와 Playwright의 `page.clock`으로 틱·정지·배속 검증 |
| DB | Testcontainers의 실제 Postgres에서 마이그레이션과 쿼리 검증 |
| 도메인 경계 | ArchUnit(또는 Spring Modulith)으로 다른 도메인 직접 접근 금지 검증 |
| 화면 흐름 (E2E) | Playwright로 시작 → 뉴스 선택 → 결과까지 실제 서버와 연결해 검증. 확률 검증은 서버 테스트가 맡는다 |
| 모바일 | Playwright 모바일 뷰포트 에뮬레이션으로 반응형 레이아웃 확인 |
| 랜덤 고정 | 테스트 프로필에서만 시드를 지정할 수 있게 한다. 운영에서는 동작하지 않게 막는다 |
