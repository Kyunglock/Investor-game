# 아키텍처 설계

> 상태: 초안 v0.1
> 표기: **(확정)** = 대화에서 정해진 것, **(제안)** = 제 판단이며 아직 합의되지 않은 것. 요구사항은 [prd.md](./prd.md), 게임 수식은 [poc.md](./poc.md)를 따른다.

## 1. 전제

| 항목 | 내용 |
|---|---|
| 플랫폼 | 반응형 웹 + PWA (확정) |
| 서버 | 있음. **판이 끝난 뒤의 결과 저장과 랭킹**만 맡는다 (확정) |
| 계정 | 없음. 익명 세션 토큰으로 결과를 묶는다 (확정) |
| 진행 상태 저장 | 서버에 저장하지 않는다. 브라우저 로컬에만 둔다 (확정) |
| 게임 로직 | 클라이언트에서 돈다. 서버는 진행 중인 판에 관여하지 않는다 (제안) |
| 한 판 | 실시간, 약 10분, 나이로 종료 (확정) |
| 작업 방식 | 도메인별 에이전트가 Orca에서 병렬로 작업 (확정) |

서버 범위를 결과 저장과 랭킹으로 좁힌 이유: 한 판이 10분이고 진행 중에는 서버와 통신할 필요가 없다. 진행 상태를 서버에 두지 않으므로 이어하기는 같은 브라우저에서만 된다. 브라우저 데이터를 지우면 진행 중이던 판은 사라지고, 이미 제출된 결과는 서버에 남는다.

능력치는 진행 상태의 일부이므로 **진행 중에는 서버에 저장하지 않는다**(확정). 능력치는 시작 시 랜덤으로 정해지고 로컬에서 성장한다.

서버에 저장하는 결과(제안): 익명 세션 ID, 최종 나이·자산·수익률, 제출 시각. 종료 시점의 능력치는 랭킹에 "이 사람은 이런 캐릭터였다"를 보여 주고 싶을 때만 결과 기록에 스냅샷으로 넣는다(선택 항목, 9절). 랭킹 기준과 검증 수준은 미결정이다(9절).

## 2. 기술 스택 (제안)

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript | 에이전트 간 계약을 타입으로 강제할 수 있다 |
| 빌드 | Vite | 설정이 단순하고 PWA 플러그인이 있다 |
| UI | React | 생태계가 크고 상태 기반 화면에 적합 |
| 테스트 | Vitest | Vite와 같이 쓰고, 엔진 확률 검증에 쓴다 |
| 진행 상태 저장 | localStorage (필요 시 IndexedDB) | 서버 없이 이어하기 |
| 서버 | TypeScript (Node) | 서버가 엔진을 재실행해 결과를 검증할 수 있다. 프레임워크와 DB는 미정 |
| PWA | 서비스 워커 + 웹 매니페스트 | 홈 화면 추가, 오프라인 실행 |

모두 제안이며, 기술 스택은 아키텍처 확정 시 한 번 더 확인한다.

## 3. 계층 구조

```
[클라이언트]
UI (React)
  │  화면 렌더, 입력, 실시간 시계 구동
  ▼
App State (게임 루프 · 로컬 저장/불러오기)
  │  틱 발생, 이벤트 큐, 일시정지/배속
  ▼
Engine (순수 로직)          Content (데이터)
  능력치 판정 · 힌트 ·        뉴스 · 직업 · 성향 이벤트 ·
  손익 · 나이/시간             힌트 문구 · 밸런스 수치
  ▲                           ▲
  │      (같은 코드 공유)      │
[서버]
API (결과 제출 · 랭킹 조회) ── 익명 세션 · 결과 저장소
  └ (검증 수준에 따라) Engine을 재실행해 결과 확인
```

클라이언트는 판이 끝나면 결과를 서버에 제출한다. 진행 중에는 서버와 통신하지 않는다.

규칙:

- **Engine은 UI와 브라우저를 모른다.** 입력과 난수 생성기를 받아 결과를 돌려주는 순수 함수로 만든다. 그래야 Node에서 시뮬레이션과 테스트가 된다.
- **난수는 주입한다.** 시드를 받는 난수 생성기를 쓰면 같은 시드로 같은 판을 재현할 수 있다(버그 재현, 밸런스 검증).
- **Content는 코드가 아니라 데이터**다. 이벤트·능력치·수치를 데이터 파일로 정의한다. 능력치 추가가 코드 변경 없이 가능해야 한다(poc.md 3절).
- **UI는 Engine을 직접 호출하지 않고 App State를 거친다.** 실시간 시계, 이벤트 대기 중 시간 정지, 저장은 App State의 책임이다.

## 4. 실시간 시간 흐름 (제안)

- App State가 틱(예: 100ms)을 발생시키고, 게임 시간은 틱마다 일정량 증가한다.
- 10분 동안 약 40년(25세→65세 가정)이면 1년이 약 15초다. 속도는 설정값이다.
- 틱마다 Engine이 "이번 시점에 발생할 이벤트가 있는가"를 판정하고, 있으면 이벤트 큐에 넣는다.
- 선택형 이벤트(뉴스, 직업 선택)가 떠 있으면 시계를 멈춘다. 알림성 이벤트는 시계를 멈추지 않고 스킵할 수 있다 (PRD 3절).
- 일시정지와 배속은 틱 증가량을 조절해서 구현한다.
- 탭이 백그라운드로 가면 시계를 멈춘다. 돌아왔을 때 한꺼번에 몰아서 시간이 흐르지 않게 한다.

## 5. 폴더 구조 (제안)

```
src/
  contracts/   공유 타입 (능력치, 이벤트, 판정 입출력). 통합 담당만 수정
  engine/      순수 로직
  content/     이벤트·문구·수치 데이터
  state/       게임 루프, 이벤트 큐, 저장
  ui/          화면, 컴포넌트, PWA 연동
server/        결과 저장, 랭킹, 익명 세션 (engine·content·contracts를 공유해서 사용)
tests/         엔진 확률 검증, 시뮬레이션
docs/          설계 문서
```

의존 방향: `ui → state → engine`, `engine`과 `state`는 `contracts`와 `content`를 읽는다. `engine`은 `ui`와 `state`를 import하지 않는다.

## 6. 에이전트 분업 (Orca)

Orca는 AI 에이전트 도구이며, 도메인별로 권한을 나눠 병렬 작업에 쓴다. 권한 단위(경로, 브랜치, 도구)는 아직 확인되지 않았다. 아래는 일반 원칙에 맞춘 제안이다.

| 담당 | 수정 가능 | 읽기 전용 | 책임 |
|---|---|---|---|
| 통합 | `src/contracts`, 설정, 의존성 | 전체 | 계약 관리, 병합, 충돌 해결 |
| 엔진 | `src/engine` | `contracts`, `content` | 판정·힌트·손익·시간 로직 |
| 콘텐츠 | `src/content` | `contracts` | 이벤트, 문구, 밸런스 데이터 |
| 상태 | `src/state` | `contracts`, `engine` | 게임 루프, 이벤트 큐, 저장 |
| UI | `src/ui` | `contracts`, `state` | 화면, 반응형, PWA, 연출 |
| 서버 | `server` | `contracts`, `engine`, `content` | 결과 저장, 랭킹, 익명 세션 |
| QA | `tests` | `src` 전체 | 확률 검증, 시뮬레이션, 밸런스 |
| 리뷰 | 없음 (지적만) | 전체 | 스타일 위반, 중복, 불필요한 추상화 지적 |
| 문서 | `docs` | 전체 | PRD, 스펙, 아키텍처 갱신 |

운영 규칙:

1. **계약이 먼저.** `src/contracts`가 확정되기 전에는 병렬 작업을 시작하지 않는다.
2. **에이전트당 브랜치(또는 워크트리) 하나.** 병합은 통합 담당이 한다.
3. **계약 변경은 통합 담당에게 요청한다.** 다른 에이전트가 직접 고치지 않는다.
4. **병합 조건:** 테스트 통과, 리뷰 에이전트 통과, 코드 스타일 준수.
5. 의존성 추가와 설정 변경은 통합 담당만 한다.

단계:

1. **0단계(직렬):** 아키텍처, 코드 스타일, 스펙, 계약 확정
2. **1단계(병렬):** 엔진 / 콘텐츠 / 상태 / UI / QA 동시 작업. UI는 상태 목(mock)으로 진행
3. **2단계(직렬):** 통합, 체감 테스트, 수치 조정

## 7. 코드 슬롭 방지 (제안)

- 코드 스타일 문서를 에이전트 공통 지침으로 둔다 (다음 문서 작업).
- 리뷰 에이전트를 병합 전 관문으로 둔다.
- 규칙 예: 요청되지 않은 추상화 금지, 데이터로 풀 수 있으면 코드로 분기하지 않기, 한 번만 쓰는 헬퍼 금지, 주석은 이유만 쓰기.
- 도메인 용어집을 만들어 같은 개념에 이름이 여러 개 붙지 않게 한다 (예: 이탈/뒤집힘, 관망/보유).
- 코드 슬롭 방지용 스킬은 코드 스타일이 정해진 뒤에 만든다. 스타일 규칙이 곧 스킬의 내용이 된다.

## 8. 테스트 전략 (제안)

| 대상 | 방법 |
|---|---|
| 판정 확률 | 시드 고정 + 대량 반복으로 기대 확률과 비교 (poc.md 9절 방식) |
| 힌트 정답률 | 안목별 정답률 검증 |
| 시간 흐름 | 가짜 시계로 틱·정지·배속 검증 |
| 저장 | 저장 후 불러오기 왕복 검증 |
| UI | 핵심 흐름(시작 → 뉴스 선택 → 결과) 수동 확인 후 필요 시 자동화 |

## 9. 미결정 사항

| # | 질문 | 영향 |
|---|---|---|
| 1 | 기술 스택 확인 (TypeScript, Vite, React) | 전체 |
| 2 | Orca의 에이전트 권한 단위 (경로 / 브랜치 / 도구) | 6절 |
| 3 | 랭킹 기준은 **최종 자산**으로 확정. 제출값을 어떻게 신뢰할지(제출값 신뢰 / 엔진 재실행 등)는 고민 중 | server |
| 3-0 | 결과 기록에 종료 시점 능력치 스냅샷을 넣을지 | server |
| 3-1 | 서버 프레임워크, DB, 호스팅 | server |
| 3-2 | 익명 세션을 잃었을 때(브라우저 데이터 삭제) 기존 결과 처리 | server |
| 4 | 시작·종료 나이와 시간 속도 | engine, state |
| 5 | 모바일 화면 크기별 레이아웃 기준 | ui |

## 10. 다음 단계

아키텍처 확정 → 코드 스타일 → 스펙(계약 포함) 순서로 진행한다.
