# 아키텍처 설계

> 상태: 초안 v0.1
> 표기: **(확정)** = 대화에서 정해진 것, **(제안)** = 제 판단이며 아직 합의되지 않은 것. 요구사항은 [prd.md](./prd.md), 게임 수식은 [poc.md](./poc.md)를 따른다.

## 1. 전제

| 항목 | 내용 |
|---|---|
| 플랫폼 | 반응형 웹 + PWA (확정) |
| 서버 | 있음. **이벤트 콘텐츠 제공**과 판이 끝난 뒤의 **결과 저장**을 맡는다. Spring Boot (확정) |
| 랭킹 | 하지 않는다 (확정). 결과 저장의 활용 방안은 나중에 정한다 |
| 콘텐츠 | 직접 작성한 이벤트 풀(뉴스 등)을 서버에 올려 두고 클라이언트가 받아 쓴다. 자동 생성은 하지 않는다 (확정) |
| 계정 | 없음. 익명 세션 토큰으로 결과를 묶는다 (확정) |
| 진행 상태 저장 | 서버에 저장하지 않는다. 브라우저 로컬에만 둔다 (확정) |
| 게임 로직 | 클라이언트에서 돈다. 서버는 진행 중인 판에 관여하지 않는다 (제안) |
| 한 판 | 실시간, 약 10분, 나이로 종료 (확정) |
| 작업 방식 | 도메인별 에이전트가 Orca에서 병렬로 작업 (확정) |

콘텐츠 제공 방식(제안): 한 판을 시작할 때 서버에서 **버전이 붙은 콘텐츠 묶음**을 받고, 그 판은 그 버전으로 끝까지 진행한다. 받은 묶음은 PWA 캐시에 보관해 오프라인에서도 시작할 수 있다. 결과를 제출할 때 콘텐츠 버전을 함께 보내고, 서버는 그 버전을 기록한다(나중에 결과를 분석할 때 기준이 된다). 이렇게 하면 앱을 다시 배포하지 않고 뉴스를 추가·수정할 수 있다.

서버 범위를 콘텐츠 제공과 결과 저장으로 좁힌 이유: 한 판이 10분이고 진행 중에는 서버와 통신할 필요가 없다. 진행 상태를 서버에 두지 않으므로 이어하기는 같은 브라우저에서만 된다. 브라우저 데이터를 지우면 진행 중이던 판은 사라지고, 이미 제출된 결과는 서버에 남는다.

능력치는 진행 상태의 일부이므로 **진행 중에는 서버에 저장하지 않는다**(확정). 능력치는 시작 시 랜덤으로 정해지고 로컬에서 성장한다.

서버에 저장하는 결과(제안): 익명 세션 ID, 콘텐츠 버전, 최종 나이·자산·수익률, 제출 시각. 종료 시점의 능력치 스냅샷은 활용 방안이 정해질 때 넣을지 결정한다(선택 항목, 9절). 결과 저장은 유지하되 활용 방안은 나중에 정한다(확정).

랭킹이 없으므로 결과 조작을 막기 위한 재실행 검증은 하지 않는다. 서버는 값의 범위와 형식을 확인하는 정도로 받는다(제안). 따라서 서버는 엔진 코드를 공유할 필요가 없다.

## 2. 기술 스택 (제안)

| 영역 | 선택 | 이유 |
|---|---|---|
| 클라이언트 언어 | TypeScript | 에이전트 간 계약을 타입으로 강제할 수 있다 |
| 빌드 | Vite | 설정이 단순하고 PWA 플러그인이 있다 |
| UI | React | 생태계가 크고 상태 기반 화면에 적합 |
| 단위 테스트 | Vitest | Vite와 같이 쓰고, 엔진 확률 검증에 쓴다 |
| E2E 테스트 | Playwright (확정) | 화면 흐름, 모바일 에뮬레이션, PWA 동작, 시계 제어 |
| 진행 상태 저장 | localStorage (필요 시 IndexedDB) | 서버 없이 이어하기 |
| 서버 | Spring Boot (Java) (확정) | 익숙한 스택이고 Flyway가 기본 통합되어 있다 |
| DB | PostgreSQL (제안) | 정형 데이터(세션, 결과, 콘텐츠 버전) 저장 |
| 마이그레이션 | Flyway (확정) | 버전 SQL 파일 방식 |
| DB 접근 | JdbcTemplate 또는 jOOQ (제안) | FK 없는 설계에서는 JPA 연관 관계 매핑이 방해가 된다 |
| 서버 요청 검증 | Bean Validation | Spring 표준 |
| 클라이언트-서버 계약 | OpenAPI (제안) | 명세에서 클라이언트용 TypeScript 타입을 생성 |
| PWA | 서비스 워커 + 웹 매니페스트 | 홈 화면 추가, 오프라인 실행 |

모두 제안이며, 기술 스택은 아키텍처 확정 시 한 번 더 확인한다.

### 2.1 DB 규칙 (확정)

- **외래 키(FK)를 쓰지 않는다.** 테이블 사이의 연결은 ID 값으로만 두고, 정합성은 애플리케이션이 지킨다. 인덱스와 유니크 제약은 사용한다.
- **Flyway 방식의 마이그레이션.** 손으로 쓴 버전 SQL 파일(`V<번호>__<설명>.sql`)을 순서대로 적용한다. 이미 적용된 파일은 수정하지 않고, 변경은 새 버전을 추가한다.
- **도메인마다 DB 스키마를 따로 가진다.** 각 도메인은 자기 스키마의 테이블만 만들고 수정한다.

제안(위 확정 사항을 지키기 위한 구체안):

- 도메인별로 Postgres 스키마(네임스페이스)와 마이그레이션 폴더를 분리한다. 예: `server/db/record/migrations/`, `server/db/content/migrations/`.
- 도메인마다 마이그레이션을 따로 실행하고, 각자 자기 스키마 안에 이력 테이블을 둔다. 에이전트가 병렬로 작업해도 **버전 번호가 충돌하지 않는다.** 하나의 번호 체계를 쓰면 서로 같은 번호를 쓰게 된다. Spring Boot에서는 스키마마다 Flyway 설정을 따로 둔다.
- 다른 도메인의 스키마는 읽지도 조인하지도 않는다. 필요하면 서버 코드에서 ID로 조회한다.
- 쿼리는 JdbcTemplate 또는 jOOQ로 작성한다. 스키마에서 마이그레이션을 만들어 주는 방식은 SQL 파일 방식과 맞지 않아 쓰지 않고, JPA의 연관 관계 매핑도 FK 없는 설계와 맞지 않아 피한다.

## 3. 계층 구조

```
[클라이언트]
UI (React)
  │  화면 렌더, 입력, 실시간 시계 구동
  ▼
App State (게임 루프 · 로컬 저장/불러오기)
  │  틱 발생, 이벤트 큐, 일시정지/배속
  ▼
Engine (순수 로직)          Content (데이터)
  능력치 판정 · 힌트 ·        뉴스 · 직업 · 성향 이벤트 ·
  손익 · 나이/시간             힌트 문구 · 밸런스 수치
  │ 판 시작: 콘텐츠 수신         │ 판 종료: 결과 제출
  ▼ (OpenAPI로 정한 계약)         ▼
[서버 · Spring Boot]
API (콘텐츠 제공 · 결과 제출) ── 콘텐츠 저장소 · 익명 세션 · 결과 저장소
```

서버는 엔진을 실행하지 않는다. 엔진과 콘텐츠 해석은 클라이언트에만 있다.

클라이언트는 판을 시작할 때 콘텐츠를 받고, 판이 끝나면 결과를 서버에 제출한다. 진행 중에는 서버와 통신하지 않는다.

규칙:

- **Engine은 UI와 브라우저를 모른다.** 입력과 난수 생성기를 받아 결과를 돌려주는 순수 함수로 만든다. 그래야 Node에서 시뮬레이션과 테스트가 된다.
- **난수는 주입한다.** 시드를 받는 난수 생성기를 쓰면 같은 시드로 같은 판을 재현할 수 있다(버그 재현, 밸런스 검증).
- **Content는 코드가 아니라 데이터**다. 이벤트·능력치·수치를 데이터 파일로 정의한다. 능력치 추가가 코드 변경 없이 가능해야 한다(poc.md 3절).
- **UI는 Engine을 직접 호출하지 않고 App State를 거친다.** 실시간 시계, 이벤트 대기 중 시간 정지, 저장은 App State의 책임이다.

## 4. 실시간 시간 흐름 (제안)

- App State가 틱(예: 100ms)을 발생시키고, 게임 시간은 틱마다 일정량 증가한다.
- 10분 동안 약 40년(25세→65세 가정)이면 1년이 약 15초다. 속도는 설정값이다.
- 틱마다 Engine이 "이번 시점에 발생할 이벤트가 있는가"를 판정하고, 있으면 이벤트 큐에 넣는다.
- 선택형 이벤트(뉴스, 직업 선택)가 떠 있으면 시계를 멈춘다. 알림성 이벤트는 시계를 멈추지 않고 스킵할 수 있다 (PRD 3절).
- 일시정지와 배속은 틱 증가량을 조절해서 구현한다.
- 탭이 백그라운드로 가면 시계를 멈춘다. 돌아왔을 때 한꺼번에 몰아서 시간이 흐르지 않게 한다.

## 5. 폴더 구조 (제안)

```
src/
  contracts/   공유 타입 (능력치, 이벤트, 판정 입출력)과 서버 API 명세(OpenAPI). 통합 담당만 수정
  engine/      순수 로직
  content/     이벤트·문구·수치 데이터. 원본은 저장소에 두고 서버가 배포·제공한다 (제안)
  state/       게임 루프, 이벤트 큐, 저장
  ui/          화면, 컴포넌트, PWA 연동
server/        Spring Boot 프로젝트. 콘텐츠 제공, 결과 저장, 익명 세션. 클라이언트 코드는 공유하지 않고 OpenAPI 명세로만 연결
tests/         엔진 확률 검증, 시뮬레이션
docs/          설계 문서
```

의존 방향: `ui → state → engine`, `engine`과 `state`는 `contracts`와 `content`를 읽는다. `engine`은 `ui`와 `state`를 import하지 않는다.

## 6. 에이전트 분업 (Orca)

Orca는 AI 에이전트 도구이며, 도메인별로 권한을 나눠 병렬 작업에 쓴다. 권한 단위(경로, 브랜치, 도구)는 아직 확인되지 않았다. 아래는 일반 원칙에 맞춘 제안이다.

| 담당 | 수정 가능 | 읽기 전용 | 책임 |
|---|---|---|---|
| 통합 | `src/contracts`, 설정, 의존성 | 전체 | 계약 관리, 병합, 충돌 해결 |
| 엔진 | `src/engine` | `contracts`, `content` | 판정·힌트·손익·시간 로직 |
| 콘텐츠 | `src/content` | `contracts` | 이벤트, 문구, 밸런스 데이터 |
| 상태 | `src/state` | `contracts`, `engine` | 게임 루프, 이벤트 큐, 저장 |
| UI | `src/ui` | `contracts`, `state` | 화면, 반응형, PWA, 연출 |
| 서버 | `server` | `contracts`(OpenAPI), `content`(제공 대상) | 콘텐츠 제공, 결과 저장, 익명 세션 |
| QA | `tests` | `src` 전체 | 확률 검증, 시뮬레이션, 밸런스 |
| 리뷰 | 없음 (지적만) | 전체 | 스타일 위반, 중복, 불필요한 추상화 지적 |
| 문서 | `docs` | 전체 | PRD, 스펙, 아키텍처 갱신 |

운영 규칙:

1. **계약이 먼저.** `src/contracts`가 확정되기 전에는 병렬 작업을 시작하지 않는다.
2. **에이전트당 브랜치(또는 워크트리) 하나.** 병합은 통합 담당이 한다.
3. **계약 변경은 통합 담당에게 요청한다.** 다른 에이전트가 직접 고치지 않는다.
4. **병합 조건:** 테스트 통과, 리뷰 에이전트 통과, 코드 스타일 준수.
5. 의존성 추가와 설정 변경은 통합 담당만 한다.

단계:

1. **0단계(직렬):** 아키텍처, 코드 스타일, 스펙, 계약 확정
2. **1단계(병렬):** 엔진 / 콘텐츠 / 상태 / UI / QA 동시 작업. UI는 상태 목(mock)으로 진행
3. **2단계(직렬):** 통합, 체감 테스트, 수치 조정

## 7. 코드 슬롭 방지 (제안)

- 코드 스타일 문서를 에이전트 공통 지침으로 둔다 (다음 문서 작업).
- 리뷰 에이전트를 병합 전 관문으로 둔다.
- 규칙 예: 요청되지 않은 추상화 금지, 데이터로 풀 수 있으면 코드로 분기하지 않기, 한 번만 쓰는 헬퍼 금지, 주석은 이유만 쓰기.
- 도메인 용어집을 만들어 같은 개념에 이름이 여러 개 붙지 않게 한다 (예: 이탈/뒤집힘, 관망/보유).
- 코드 슬롭 방지용 스킬은 코드 스타일이 정해진 뒤에 만든다. 스타일 규칙이 곧 스킬의 내용이 된다.

## 8. 테스트 전략 (제안)

| 대상 | 방법 |
|---|---|
| 판정 확률 | 시드 고정 + 대량 반복으로 기대 확률과 비교 (poc.md 9절 방식) |
| 힌트 정답률 | 안목별 정답률 검증 |
| 시간 흐름 | 가짜 시계로 틱·정지·배속 검증 |
| 저장 | 저장 후 불러오기 왕복 검증 |
| 화면 흐름 (E2E) | Playwright로 시작 → 뉴스 선택 → 결과 → 결과 제출까지 자동 검증. 엔진 확률 검증은 Vitest가 맡고 Playwright에서는 하지 않는다 |
| 시계 | Playwright의 `page.clock`으로 시간을 감아 10분 판을 짧게 테스트 |
| 모바일 | Playwright 모바일 뷰포트 에뮬레이션으로 반응형 레이아웃 확인 |
| 랜덤 고정 | 테스트에서만 시드를 지정하는 장치(URL 파라미터 또는 테스트 훅)를 둔다. 프로덕션에서는 동작하지 않게 막는다 |
