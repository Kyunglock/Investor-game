# 코드 스타일

> 상태: 초안 v0.1 (기본안)
> 표기: **(확정)** = 대화에서 정해진 것, **(제안)** = 기본안으로 제가 정한 것. 모두 제안인 항목은 표기를 생략한다.
> 이 문서는 AI 에이전트(agent1~agent5)와 사람 모두가 따르는 공통 규칙이다. 구조는 [architecture.md](./architecture.md), 도메인은 [domains.md](./domains.md), DB는 [db.md](./db.md)를 따른다.

## 1. 기본 원칙

1. **요청한 것만 만든다.** 요청되지 않은 기능, 설정 옵션, 확장 지점을 추가하지 않는다.
2. **고치기 전에 읽는다.** 같은 일을 하는 코드가 이미 있는지 먼저 찾고, 있으면 그것을 쓴다. 새 헬퍼를 만들기 전에 검색한다.
3. **주변 코드처럼 쓴다.** 같은 모듈의 이름, 구조, 주석 밀도, 에러 처리 방식을 따른다.
4. **가장 단순한 것으로 시작한다.** 추상화는 같은 형태가 세 번 반복된 뒤에 만든다.
5. **범위를 지킨다.** 자기 에이전트의 소유 범위(architecture.md 8절) 밖은 수정하지 않는다. 필요하면 PR 댓글로 요청한다.
6. **확인하고 보고한다.** 테스트를 실행하고 결과를 그대로 보고한다. 실행하지 않은 것을 통과했다고 쓰지 않는다.

## 2. 코드 슬롭 금지 목록

AI가 만든 코드에서 반복되는 패턴이다. 발견되면 리뷰에서 반려한다.

| 패턴 | 규칙 |
|---|---|
| 쓰이지 않는 추상화 | 구현이 하나뿐인 인터페이스, 한 곳에서만 쓰는 팩토리·빌더·전략, "나중에 필요할 것 같은" 확장 지점을 만들지 않는다 |
| 한 번만 쓰는 헬퍼 | 호출이 한 곳뿐인 유틸 함수·클래스를 분리하지 않는다 |
| 과한 방어 코드 | 내부 호출에서 타입이 보장하는 값에 null 검사, try-catch, 기본값 대체를 넣지 않는다. 검증은 시스템 경계(API 입력, 외부 데이터)에서만 한다 |
| 에러 삼키기 | `catch` 후 로그만 남기고 계속하지 않는다. 처리할 수 없으면 던진다 |
| 설명하는 주석 | 코드가 무엇을 하는지 반복하는 주석을 달지 않는다. 주석은 **왜**(비자명한 제약, 이유)만 쓴다 |
| 작업 기록 주석 | "수정함", "추가됨", `// TODO: 나중에` 같은 주석을 남기지 않는다. 변경 이력은 git이 보관한다 |
| 죽은 코드 | 주석 처리한 코드, 쓰이지 않는 import·변수·메서드를 남기지 않는다 |
| 하위 호환 껍데기 | 아직 배포되지 않은 코드에 호환용 래퍼, 사용 중단 표시, 이전 이름 별칭을 만들지 않는다 |
| 범위 밖 수정 | 요청과 무관한 리팩터링, 포맷 변경, 이름 바꾸기를 같이 하지 않는다 |
| 중복 정의 | 같은 개념에 이름을 둘 이상 붙이지 않는다. 용어집(domains.md 6절)의 용어를 쓴다 |
| 일반론적 이름 | `Manager`, `Helper`, `Util`, `Handler`, `Processor`, `Data`, `Info`를 의미 없이 이름에 붙이지 않는다 |
| 과한 로그 | 함수 진입·종료마다 로그를 남기지 않는다. 운영에서 필요한 사건(판 시작·종료, 거부된 요청, 예외)만 남긴다 |
| 장황한 설명 응답 | 코드 외에 변경 이유를 길게 늘어놓지 않는다. 변경 요약은 PR 설명에 쓴다 |
| 가짜 테스트 | 아무것도 검증하지 않는 테스트, 구현을 그대로 베낀 기대값, 항상 통과하는 단언을 쓰지 않는다 |
| 없는 것을 있는 것처럼 | 존재하는지 확인하지 않은 API, 메서드, 설정 키를 쓰지 않는다. 라이브러리 사용법은 문서나 소스로 확인한다 |

## 3. 서버 (Java, Spring Boot)

### 3.1 기본 설정 (제안)

| 항목 | 내용 |
|---|---|
| Java | 21 (LTS) |
| 빌드 | Gradle. 빌드 스크립트 언어(Groovy / Kotlin DSL)는 통합 담당이 결정한다 (12절) |
| 포맷 | Spotless + google-java-format. 포맷은 도구가 정하고 사람이 논쟁하지 않는다 |
| 정적 검사 | 컴파일러 경고를 오류로 처리 (`-Werror`) |
| 의존성 | 통합 담당만 추가한다 |

### 3.2 패키지 구조 (확정)

전체 폴더 구조는 architecture.md 6절을 따른다. 도메인 하나는 다음 구조를 가진다.

```
investorgame/asset/
  AssetService.java          공개 인터페이스. 다른 도메인이 호출하는 유일한 입구
  Trade.java ...             공개 입력·출력 타입 (record)
  internal/                  나머지 전부 (구현, 저장소, 행 매핑). 다른 도메인이 import하면 빌드 실패
```

- 도메인 우선으로 나눈다. `controller/service/repository` 같은 계층 폴더로 나누지 않는다.
- 다른 도메인은 `<Domain>Service`와 공개 record만 사용한다. `internal` 패키지는 import하지 않는다 (ArchUnit으로 강제).
- 도메인 사이의 호출은 진행(`progress`)에서만 한다 (domains.md 3절).
- `api` 패키지는 컨트롤러, 요청·응답 변환, 전역 예외 처리만 둔다. 규칙 판단을 두지 않는다.
- `common`에는 두 도메인 이상이 실제로 쓰는 코드만 둔다(시드 유도, 공통 예외 등). 도메인 규칙과 게임 수치는 넣지 않는다.
- `common`, `config`, `architecture` 테스트는 통합 담당이 소유한다. 추가가 필요하면 PR 댓글로 요청한다.

### 3.3 언어 사용

- **불변을 기본으로 한다.** 값 객체와 입출력은 `record`를 쓴다. 가변 클래스는 상태를 관리해야 할 때만 쓴다.
- **`null`을 인자와 반환값으로 쓰지 않는다.** 없을 수 있는 반환은 `Optional`, 필수 인자는 생성 시 검증한다. 필드로는 `Optional`을 쓰지 않는다.
- **`var`는 오른쪽 식에서 타입이 분명할 때만** 쓴다.
- 주입은 생성자 주입만 쓴다. 필드 주입(`@Autowired` 필드)을 쓰지 않는다. Lombok은 쓰지 않는다 (`record`와 IDE 생성으로 충분하다).
- 문자열 코드 값(`"BUY"`)을 흩뿌리지 않는다. 서버가 의미를 아는 고정 값은 `enum`이나 상수로 한 곳에서 정의한다. DB에 저장하는 코드는 db.md 1절을 따른다.
- 매직 넘버를 쓰지 않는다. 확률 계수, 매수 비율 같은 게임 수치는 설정으로 빼고 이름을 붙인다 (poc.md 5절).

### 3.4 난수와 시간

- 난수는 직접 만들지 않는다. 판 시드에서 유도한 `RandomGenerator`를 **인자로 받는다** (db.md 3.2절). `Math.random()`, `new Random()`, `ThreadLocalRandom`은 금지.
- 현재 시각을 도메인 로직에서 읽지 않는다. 게임 시각은 보고된 값으로만 계산한다 (architecture.md 4절). 기록용 `created_at` 같은 값만 시스템 시각을 쓴다.
- 이 두 규칙 덕분에 같은 입력이면 같은 결과가 나온다. 테스트와 재현이 쉬워진다.

### 3.5 트랜잭션과 예외

- 트랜잭션 경계는 진행의 서비스 메서드에 둔다. 한 요청이 한 트랜잭션이다 (db.md 5절). 다른 도메인의 서비스는 트랜잭션을 새로 시작하지 않는다.
- 예외는 의미 있는 타입으로 던진다. 사용자 입력 오류는 4xx로 변환하고, 불변식이 깨진 경우는 5xx로 둔다. 변환은 `api` 계층의 한 곳(전역 예외 처리)에서 한다.
- 예외 메시지에 내부 값(숨은 방향, 확률, 시드)을 담지 않는다. 클라이언트에 노출되면 안 된다 (architecture.md 5절).

### 3.6 데이터 접근

- 쿼리는 도메인의 `internal` 저장소에서만 실행한다. 컨트롤러와 서비스에 SQL을 쓰지 않는다.
- 자기 도메인 접두사의 테이블만 읽고 쓴다. 다른 도메인 테이블을 조인하지 않는다 (db.md 1절).
- JPA 연관 관계 매핑과 스키마 자동 생성을 쓰지 않는다 (확정).
- 파라미터는 항상 바인딩한다. 문자열 이어 붙이기로 SQL을 만들지 않는다.
- 조회는 필요한 컬럼만 가져온다. 목록 조회에는 상한을 둔다.

### 3.7 이름

| 대상 | 규칙 | 예 |
|---|---|---|
| 클래스·record | 명사, PascalCase | `Holding`, `DeviationReason` |
| 메서드 | 동사로 시작, camelCase | `applyTrade`, `findPendingEvents` |
| 상수 | UPPER_SNAKE_CASE | `BUY_RATIO` |
| 테스트 | 동작과 조건을 한글로 | `줏대가_0이면_다른_뉴스를_따른다()` |
| 패키지 | 소문자 한 단어, 도메인 이름 그대로 | `asset`, `event` |

## 4. 클라이언트 (TypeScript, React)

### 4.1 기본 설정 (제안)

| 항목 | 내용 |
|---|---|
| TypeScript | `strict` 켬. `any` 금지(불가피하면 이유를 주석으로). `unknown`을 쓰고 좁힌다 |
| 포맷·린트 | Biome. 포맷은 도구가 정한다 |
| 모듈 | named export만 쓴다. default export를 쓰지 않는다 |
| 의존성 | 통합 담당만 추가한다 |

### 4.2 구조

```
web/src/
  features/<기능>/      화면 단위 기능 (components, hooks, store 한 곳에)
  shared/               여러 기능이 쓰는 컴포넌트·훅·유틸
  api/                  OpenAPI에서 생성한 타입과 클라이언트 (직접 수정하지 않는다)
```

- **게임 규칙, 확률, 숨은 값을 클라이언트에 두지 않는다** (확정, architecture.md 7절). 클라이언트가 아는 것은 시계, 화면, 서버 응답이다.
- 서버 응답 타입은 생성된 타입을 그대로 쓴다. 같은 모양의 타입을 손으로 다시 정의하지 않는다.
- 클라이언트의 판단은 표시 로직까지만 한다. 손익 계산, 능력치 판정, 이벤트 선택을 흉내 내지 않는다.

### 4.3 React

- 함수 컴포넌트와 훅만 쓴다. 클래스 컴포넌트를 쓰지 않는다.
- 컴포넌트는 표시만 한다. 서버 호출과 시계 구동은 훅이나 store에 둔다.
- 상태는 가장 가까운 곳에 둔다. 전역 store(Zustand)는 여러 화면이 공유하는 값(현재 게임 시각, 진행 중인 판)에만 쓴다.
- `useEffect`는 외부 시스템과 동기화할 때만 쓴다. 값을 계산하거나 파생 상태를 만드는 데 쓰지 않는다 (렌더 중 계산한다).
- `useMemo`, `useCallback`은 측정으로 필요가 확인된 곳에만 쓴다.
- 스타일은 Tailwind를 쓴다. 인라인 스타일과 임의 CSS 파일을 섞지 않는다.
- 모든 상호작용 요소는 키보드로 조작할 수 있고, 아이콘만 있는 버튼에는 라벨을 단다.

### 4.4 이름

| 대상 | 규칙 | 예 |
|---|---|---|
| 컴포넌트 | PascalCase, 파일 이름과 같게 | `NewsCard.tsx` |
| 훅 | `use` 접두사 | `useGameClock` |
| 함수·변수 | camelCase | `submitChoice` |
| 타입 | PascalCase, `I` 접두사 금지 | `PendingEvent` |
| 상수 | UPPER_SNAKE_CASE | `REPORT_INTERVAL_DAYS` |

## 5. SQL과 마이그레이션

- 위치와 이름은 db.md 6절을 따른다. 예: `V202610171030__asset_init.sql`.
- **FK 제약(`REFERENCES`, `FOREIGN KEY`)을 쓰지 않는다** (확정).
- 적용된 마이그레이션 파일은 수정하지 않는다 (확정). 변경은 새 파일을 추가한다.
- 자기 도메인 접두사의 테이블만 만든다.
- 하나의 마이그레이션은 하나의 목적만 가진다. 스키마 변경과 데이터 이전을 한 파일에 섞지 않는다.
- 이름은 소문자 snake_case. 키워드를 대문자로 쓴다. 한 줄에 한 컬럼을 쓴다.
- 인덱스는 실제 조회 패턴이 있는 것만 만든다. 이유를 db.md에 적는다.

## 6. API (OpenAPI)

- 명세가 먼저다. 명세(`contracts/openapi`)가 정해지기 전에는 컨트롤러와 클라이언트를 구현하지 않는다 (architecture.md 8절).
- 계약 변경은 통합 담당만 한다. 다른 에이전트는 PR 댓글로 요청한다.
- 응답에 규칙 정보(확률, 숨은 방향, 시드)를 담지 않는다. 화면에 필요한 값만 담는다.
- 필드 이름은 camelCase, 날짜·시각은 ISO 8601, 금액은 정수(원)다.
- 오류는 일관된 하나의 형식으로 돌려준다.

## 7. 테스트

| 대상 | 방법 |
|---|---|
| 규칙·확률 | 시드를 고정하고 대량 반복해 기대 확률과 비교한다 (poc.md 9절 방식). 한 번의 우연한 결과로 단언하지 않는다 |
| DB | Testcontainers의 실제 Postgres를 쓴다. DB를 모의 객체로 대체하지 않는다 |
| 도메인 경계 | ArchUnit으로 `internal` 접근, 도메인 간 직접 호출을 검사한다 |
| 클라이언트 | 표시 로직은 Vitest, 화면 흐름은 Playwright |

- 테스트는 구현 방식이 아니라 **동작**을 검증한다. 구현을 베낀 기대값을 쓰지 않는다.
- 하나의 테스트는 하나의 이유로 실패한다. 이름만 보고 무엇이 깨졌는지 알 수 있어야 한다.
- 우리 코드를 모의 객체로 대체하지 않는다. 외부 경계(시간, 난수는 주입으로 해결)만 대체한다.
- 버그를 고칠 때는 그 버그를 재현하는 테스트를 먼저 추가한다.
- 통과하지 않는 테스트를 지우거나 건너뛰기로 바꾸지 않는다. 원인을 고친다.

## 8. 주석과 문서

- 주석은 **왜**만 쓴다. 코드로 표현할 수 있으면 이름을 고쳐서 해결한다.
- 공개 인터페이스(`<Domain>Service`)에는 입력·출력·실패 조건을 간단히 적는다.
- 문서(`docs/`)는 코드와 어긋나면 같은 PR에서 고친다.
- 이모지, 장식용 구분선, 과장된 표현을 쓰지 않는다.

## 9. Git과 PR

- **커밋 메시지와 PR 설명은 한글**로 쓴다 (확정). `docs:`, `feat:`, `fix:` 같은 접두사는 영문 그대로 두고 설명은 한글로 쓴다.
- 커밋은 하나의 목적만 가진다. 제목은 무엇을 했는지, 본문은 **왜** 했는지를 쓴다.
- 브랜치 이름은 `agent<번호>/<주제>` 형식을 쓴다 (제안). 예: `agent2/asset-ledger`.
- PR은 작게 유지한다. 리뷰하기 어려울 만큼 커지면 나눈다.
- 도메인에 걸친 변경은 PR을 만들고 `cross-domain` 라벨을 붙인다. 영향받는 도메인 소유자가 PR 댓글로 협의한다 (확정).
- 병합 조건: 테스트 통과, 리뷰 통과, 스타일 검사 통과, 도메인 경계 검사 통과, 소유 경로 검사 통과.
- 시크릿(토큰, 비밀번호)을 커밋하지 않는다.

## 10. 에이전트 작업 규칙

1. 작업 전에 해당 도메인의 스펙(`docs/specs/`)과 이 문서를 읽는다.
2. 소유 범위 밖 파일이 필요하면 수정하지 않고 PR 댓글로 요청한다.
3. 모르는 것은 가정하지 말고 묻는다. 특히 계약, 수치, 규칙은 추측하지 않는다.
4. 구현 후 테스트를 실행하고 **실제 출력을 근거로** 보고한다.
5. 작업 보고는 짧게 쓴다. 한 일, 확인한 방법, 남은 문제 순서로 쓴다.
6. 미완성이거나 건너뛴 부분은 숨기지 말고 그대로 밝힌다.

## 11. 리뷰 체크리스트

리뷰 담당과 슬롭 방지 스킬이 같은 기준을 쓴다. 병합 전에 하나라도 걸리면 반려한다.

**범위**
- [ ] 요청된 것만 바꿨는가? 요청 밖 리팩터링·포맷 변경이 없는가
- [ ] 소유 경로 밖을 수정하지 않았는가
- [ ] 계약(OpenAPI)과 공개 인터페이스 변경이 PR에서 합의되었는가

**단순함**
- [ ] 구현이 하나뿐인 인터페이스, 한 곳에서만 쓰는 헬퍼가 없는가
- [ ] 쓰이지 않는 코드, 주석 처리한 코드, 쓰이지 않는 import가 없는가
- [ ] 내부 호출에 불필요한 null 검사·try-catch가 없는가
- [ ] 이미 있는 코드를 다시 만들지 않았는가

**정확함**
- [ ] 난수를 주입받고 현재 시각을 도메인 로직에서 읽지 않는가
- [ ] 규칙 정보(확률, 숨은 값, 시드)가 응답, 로그, 예외 메시지에 새지 않는가
- [ ] FK가 없고, 다른 도메인 테이블을 읽지 않는가
- [ ] 존재하지 않는 API·설정을 쓰지 않았는가

**테스트**
- [ ] 새 동작에 테스트가 있고, 동작을 검증하는가 (구현을 베끼지 않았는가)
- [ ] 테스트를 실제로 실행했고 결과가 보고되었는가
- [ ] 테스트를 지우거나 건너뛰기로 바꾸지 않았는가

**글**
- [ ] 주석이 "왜"만 설명하는가. 작업 기록 주석이 없는가
- [ ] 용어집의 용어를 썼는가
- [ ] 커밋 메시지와 PR 설명이 한글인가
