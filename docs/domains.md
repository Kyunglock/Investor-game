# 도메인 설계

> 상태: 초안 v0.1
> 표기: **(확정)** = 대화에서 정해진 것, **(제안)** = 제 판단이며 아직 합의되지 않은 것. 구조는 [architecture.md](./architecture.md), 요구사항은 [prd.md](./prd.md), 게임 규칙은 [poc.md](./poc.md)를 따른다.

## 1. 분할 기준

도메인은 게임 개념의 이름이 아니라 아래 기준으로 나눈다.

1. **상태 소유권.** 상태를 바꿀 수 있는 도메인은 하나뿐이다. 다른 도메인은 서비스 인터페이스로만 읽거나 요청한다.
2. **같이 바뀌는 것끼리 묶는다.** 같은 이유로 수정되는 규칙은 같은 도메인에 둔다.
3. **도메인 사이의 호출을 줄인다.** 도메인은 서로를 직접 호출하지 않고 **진행이 값을 전달**한다 (아래 3절). 그래야 에이전트들이 병렬로 작업해도 서로의 코드를 기다리지 않는다.
4. **서버에 있는 것만 도메인이다.** 시계와 화면은 클라이언트의 일이다 (확정).

모든 도메인은 서버 안의 모듈이다. 모듈형 모놀리스로 가며 MSA 분리는 목표가 아니다 (확정). DB는 **하나의 스키마**를 쓰고, 도메인은 이름 접두사로 자기 테이블을 구분한다 (확정, FK 없음). 접두사는 도메인 이름과 같다 (예: `asset_account`).

## 2. 도메인 목록

### 게임 규칙 도메인 (5개)

| 도메인 | 소유하는 상태 | 책임 | 테이블 접두사 |
|---|---|---|---|
| 캐릭터 | 능력치 5종, 성장 경험, 직업, 관심 섹터(투자 성향) | 랜덤 생성, 성장 규칙, 직업·관심 섹터 확정 | `character_` |
| 자산 | 현금, 종목별 수량·원가, 빚, 장부 | 수량·가격 매매, 수입·지출·이자, 평가·총자산 (가격은 인자) | `asset_` |
| 시장 | 종목 현재가, 월별 이력 | 매월 추세+잡음 변동, 뉴스 충격 반영, 시세·이력 조회. 콘텐츠(종목)를 직접 읽는다 | `market_` |
| 가계 | 결혼일, 자녀, 은퇴일 | 월 생활비·배우자 소득·결혼·출산 비용 계산 (물가 포함) | `household_` |
| 이벤트 운영 | 발생한 이벤트 인스턴스(숨은 방향·변동 폭 포함), 노출 이력 | 이벤트 발생 시점과 종류 결정, 관심 섹터 노출 비중, 스킵 가능 여부, 선택지 구성 | `event_` |
| 행동 | 없음 (순수 규칙) | 선택이 뒤집히는 판정(줏대 → 인내심/용기), 안목 힌트 문구 생성 | 없음 |
| 진행 | 판 상태: 마지막 보고 시각, 단계, 판 시드, 종료 여부 | 시각 보고 검증, 단계 전환, 한 요청의 처리 순서 조율, 종료 판정 | `progress_` |

### 플랫폼 도메인 (3개)

| 도메인 | 소유하는 상태 | 책임 | 테이블 접두사 |
|---|---|---|---|
| 세션 | 익명 세션 | 발급과 확인 | `session_` |
| 콘텐츠 | 직접 작성한 이벤트 풀, 콘텐츠 버전 | 콘텐츠 로드와 조회 (원본은 저장소의 `content/`) | `content_` |
| 결과 | 판 결과 기록 | 판 종료 시 결과 저장 | `result_` |

### 도메인이 아닌 것

| 대상 | 위치 |
|---|---|
| 시계, 나이 표시, 일시정지, 배속 | 클라이언트 (확정) |
| 화면, 연출, PWA | 클라이언트 |
| API 요청·응답 변환 | `api` 계층 (도메인 로직을 두지 않는다) |

## 3. 도메인 사이의 호출 규칙 (제안)

**진행만 다른 게임 규칙 도메인을 호출한다.** 캐릭터, 자산, 이벤트 운영, 행동은 서로를 호출하지 않는다. 필요한 값은 진행이 읽어서 인자로 넘긴다.

```
api ─→ 세션 (확인)
   └─→ 진행 ─→ 캐릭터
             ├→ 자산
             ├→ 이벤트 운영 ─→ 콘텐츠
             ├→ 행동
             └→ 결과 (판 종료 시)
```

허용되는 의존은 위 화살표뿐이다. 도메인 간 직접 호출은 **이벤트 운영→콘텐츠, 시장→콘텐츠** 둘만 허용한다 (2026-10-18 시장 도메인 추가 때 늘림). 진행은 시장·가계도 부른다.

이렇게 하면 행동은 능력치와 이벤트 값을 **입력으로 받아 결과를 돌려주는 순수 함수**가 되어 단독으로 개발·테스트할 수 있다. 자산도 "어떤 금액을 매수한다"만 알고 직업이나 능력치를 모른다.

### 처리 흐름 1: 시간 경과 보고 (`advance`)

1. 진행이 보고된 시각을 검증한다 (역행 금지, 한 번에 건너뛰는 상한).
2. 진행이 캐릭터에서 직업·관심 섹터를 읽는다.
3. 진행이 자산에 구간의 월급 입금을 요청한다. 월급 액수는 직업 정보에서 얻어 인자로 넘긴다.
4. 진행이 이벤트 운영에 "이 구간에 발생할 이벤트"를 요청한다. 관심 섹터를 인자로 넘긴다.
5. 진행이 단계 전환(저축 → 투자 시작)과 종료 여부를 판단한다.
6. 진행이 변경 결과를 응답으로 묶는다. 이벤트의 숨은 값은 응답에 넣지 않는다.

### 처리 흐름 2: 선택 제출 (`choices`)

1. 진행이 이벤트 운영에서 해당 이벤트(숨은 값 포함)를 읽는다.
2. 진행이 캐릭터에서 능력치를 읽는다.
3. 진행이 행동에 `(선택, 능력치, 이벤트, 난수)`를 넘겨 **실제 행동과 원인**을 받는다.
4. 진행이 자산에 실제 행동을 요청한다. 자산이 매수·매도와 주가 변동을 반영하고 손익을 돌려준다.
5. 진행이 캐릭터에 이탈 사유를 넘겨 능력치 성장을 반영한다.
6. 진행이 응답으로 "선택 → 실제 행동, 원인 문구, 손익"을 묶는다.

## 4. 도메인별 요약

각 도메인의 입출력과 규칙 상세는 `docs/specs/<도메인>.md`에서 정한다. 아래는 스펙의 출발점이다.

### 캐릭터

- 능력치 5종: 안목, 인내심, 용기, 줏대, 운 (확정). 운은 성장하지 않는다 (확정).
- 능력치 범위와 초기값은 랜덤이다 (poc.md: 15~85 가정).
- 성장은 이탈 경험으로 조금씩 오르는 안이 있다 (poc.md 7절, 미확정).
- 직업과 관심 섹터를 보관한다. 둘 다 이벤트의 결과로 확정된다 (prd 3절).
- 능력치 추가는 코드 변경 없이 설정으로 가능해야 한다 (확정).

### 자산

- 매수 금액, 월급, 주가 변동 폭 등은 설정값이다.
- 직업은 **돈을 버는 수단**이며 섹터와 무관하다 (확정). 자산은 직업을 모르고 월급 액수만 받는다.
- 총자산은 현금과 보유 평가액의 합이다.

### 이벤트 운영

- 뉴스 이벤트는 선택형이며 스킵할 수 없다 (확정). 알림성 이벤트는 스킵할 수 있다 (확정).
- 뉴스의 숨은 방향(오름·내림)과 변동 폭은 서버가 정하고 클라이언트에는 내려보내지 않는다.
- 관심 섹터 뉴스를 더 자주 노출하되, 다른 섹터 뉴스도 일부 섞는다 (확정 방향, 비중은 미정).
- 줏대 판정용 "다른 뉴스"도 이벤트 운영이 함께 만든다.

### 행동

- 판정 순서: 줏대 → (관망이면 인내심, 매수·매도면 용기) (poc.md 4~5절).
- 뒤집힘의 원인을 항상 결과로 돌려준다. 원인이 보이지 않는 억울함은 이탈로 이어진다 (prd 목표).
- 안목 힌트는 확률 숫자 없이 애매한 문구로 준다 (확정).
- 상태가 없으므로 DB 테이블이 없다.

### 진행

- 시계는 클라이언트가 구동하고, 진행은 보고된 시각만 믿고 검증한다.
- 종료 조건은 나이이다 (확정).
- 판 시드는 서버가 만든다. 같은 시드와 같은 보고·선택 순서면 판이 재현된다.

### 세션 / 콘텐츠 / 결과

- 세션: 계정 없는 익명 세션. 진행 중인 판과 결과를 세션에 묶는다 (확정).
- 콘텐츠: 이벤트 풀을 직접 작성한다 (확정). 판마다 사용한 콘텐츠 버전을 진행이 기록한다.
- 결과: 결과 저장은 유지하되 활용 방안은 나중에 정한다 (확정).

## 5. 에이전트 매핑

구현 에이전트는 **4개**로 시작한다 (확정).

| 에이전트 | 맡는 범위 | 묶은 이유 |
|---|---|---|
| 판정 | 캐릭터 + 행동 | 행동은 능력치를 입력으로 판정하고, 성장 규칙은 이탈 원인에 따라 능력치를 바꾼다. 확률 검증을 한 곳에서 한다 |
| 시장·이벤트 | 자산 + 이벤트 운영 | 뉴스 이벤트의 숨은 방향과 변동 폭을 자산이 주가 변동에 적용한다 |
| 플랫폼 | 세션, 콘텐츠, 결과 + `content/` 이벤트 작성 | 서로 독립적이고 일이 가볍다 |
| 클라이언트 | `web/` (E2E 포함, 도메인 아님) | OpenAPI 목(mock)으로 독립 |

- **진행 도메인**은 모든 도메인을 엮는 조율 역할이라 2단계에서 구현한다. 판정이나 시장·이벤트 에이전트 중 먼저 끝난 쪽이 이어서 맡는다.
- 도메인 사이의 호출이 진행에만 모이므로, 판정과 시장·이벤트 에이전트는 인터페이스만 합의되면 서로 기다리지 않는다.
- 도메인 경계는 에이전트 수와 무관하게 빌드에서 강제한다.

## 6. 용어집 (제안)

같은 개념에 이름이 둘 이상 붙지 않도록 처음부터 고정한다.

| 용어 | 뜻 | 쓰지 않는 표현 |
|---|---|---|
| 선택 | 사용자가 누른 매수·매도·관망 | 입력, 명령 |
| 실제 행동 | 판정을 거쳐 실제로 일어난 행동 | 결과 행동, 최종 선택 |
| 이탈 | 선택과 실제 행동이 다른 것 | 뒤집힘, 오버라이드 (코드 용어는 이탈로 통일) |
| 이탈 원인 | 어떤 능력치 때문에 이탈했는가 | 사유 |
| 관망 | 보유하지도 사지도 않고 지켜보는 선택 | 홀드, 대기 |
| 이벤트 | 게임 중 발생하는 모든 사건 | 사건, 뉴스 (뉴스는 이벤트의 한 종류) |
| 뉴스 이벤트 | 선택형 이벤트 | 뉴스 기사 |
| 알림성 이벤트 | 선택이 필요 없고 스킵 가능한 이벤트 | 알림 |
| 힌트 | 안목 기반 애매한 문구 | 팁, 예측 |
| 판 | 한 번의 플레이 (시작부터 종료까지) | 게임 세션, 라운드 |
| 세션 | 익명 접속 식별 단위 | 계정, 유저 |

## 7. 미결정 사항

| # | 질문 | 영향 |
|---|---|---|
| 1 | 직업은 캐릭터가 갖는 것이 맞는지, 월급은 직업 정보(콘텐츠)에서 오는지 | 캐릭터, 자산, 콘텐츠 |
| 2 | 관심 섹터를 정하는 규칙 (성향 이벤트 선택의 어떤 값으로 정하나) | 캐릭터, 이벤트 운영 |
| 3 | 단계 전환 규칙의 정확한 조건 (시간, 자산, 사용자 수락) | 진행 |
| 4 | 능력치 성장 방식 | 캐릭터, 행동 |
| 5 | 보고 구간 크기와 건너뛰기 상한 | 진행 |
| 6 | 결과에 능력치 스냅샷을 넣을지 | 결과 |

## 8. 다음 단계
