# 도메인 설계

> 상태: v0.2 (증권사 육성 구조로 개정, 2026-11-05. #292에서 옛 인생 시뮬레이터의 도메인을, decisions.md 228번에서 3분 육성 판을 지운 뒤)
> 표기: **(확정)** = 대화에서 정해진 것, **(제안)** = 제 판단이며 아직 합의되지 않은 것. 구조는 [architecture.md](./architecture.md), 게임 설계는 [증권사 육성 설계](./superpowers/specs/2026-11-05-brokerage-raising-design.md), 결정은 [decisions.md](./decisions.md) 197번부터(228번부터가 지금 흐름)를 따른다.

## 1. 분할 기준

도메인은 게임 개념의 이름이 아니라 아래 기준으로 나눈다.

1. **상태 소유권.** 상태를 바꿀 수 있는 도메인은 하나뿐이다. 다른 도메인은 서비스 인터페이스로만 읽거나 요청한다.
2. **같이 바뀌는 것끼리 묶는다.** 같은 이유로 수정되는 규칙은 같은 도메인에 둔다. 공채 시장·투자 회의·결산·매각은 같은 회사 상태와 같은 등급표·같은 돈을 쓰므로 한 도메인(육성)에 둔다 (decisions.md 208·228번).
3. **도메인 사이의 호출을 줄인다.** 다른 도메인을 부르는 것은 **육성 하나**다. 행동·콘텐츠·세션은 혼자 선다 (3절).
4. **서버에 있는 것만 도메인이다.** 화면과 그림은 클라이언트의 일이다 (확정).

모든 도메인은 서버 안의 모듈이다. 모듈형 모놀리스로 가며 MSA 분리는 목표가 아니다 (확정). DB는 **하나의 스키마**를 쓰고, 도메인은 이름 접두사로 자기 테이블을 구분한다 (확정, FK 없음). 접두사는 도메인 이름과 같다 (예: `raising_company`).

## 2. 도메인 목록

| 도메인 | 패키지 | 소유하는 상태 | 책임 | 테이블 |
|---|---|---|---|---|
| 육성 | `raising` | 회사, 세션의 기억 | 증권사를 조율한다. 회사 차리기(망하면 다시 차리기), 공채 시장, 배치, 이직 제안, 투자 회의, 결산, 라이벌·연표. 매각·명성 규칙은 엔진에 남았지만 API가 부르지 않는다(236번) | `raising_company`, `raising_memory` |
| 행동 | `behavior` | 없음 (순수 규칙) | 판정 한 번의 뒤집힘 확률, 안목의 정답률과 힌트(형광펜) | 없음 |
| 콘텐츠 | `content` | 콘텐츠 버전 기록 | `content/` JSON을 서버 시작 때 읽어 검증하고 메모리에 둔다. 조회 | `content_version` |
| 세션 | `session` | 익명 세션 | 발급과 확인, 최근 세션 목록(관리자) | `session_info` |

이름이 "육성"인 까닭: 처음에는 사람을 3분 동안 키워 회사에 넣는 게임이었다. 3분 육성 판은 228번에서 없앴지만 패키지·테이블 이름(`raising`)은 그대로 둔다.

### 도메인이 아닌 것

| 대상 | 위치 |
|---|---|
| 화면, 그림(사무실·도트 사람·이사 장면), 그림 끄기, 자동 배치, PWA | 클라이언트 |
| API 요청·응답 변환, 관리자 토큰, 플레이 로그 | `api` 계층 (도메인 로직을 두지 않는다) |
| 두 도메인 이상이 쓰는 값 타입, 시드 난수, 공통 예외 | `common` |

### 지운 도메인과 판 (기록)

옛 인생 시뮬레이터의 도메인은 **#292에서 코드를 지웠다** (decisions.md 227번). 3분 육성 판은 **228번에서 지웠다**. 스펙은 [specs/](./specs/README.md)에 기록으로 남고, 테이블은 DB에 남아 있지만 코드가 쓰지 않는다 ([db.md](./db.md) 2.2절).

| 지운 것 | 맡던 것 | 지금 어디로 |
|---|---|---|
| 진행 (`progress`) | 판 조율, 시각 보고, 나이로 종료 | 조율은 육성이 맡는다. 시계와 나이는 없다 |
| 캐릭터 (`character`) | 능력치, 성장, 직업, 성향 | 능력치는 회사 상태(JSON)의 직원·지원자에 있다. 성장·직업·성향은 없다 |
| 자산 (`asset`) | 현금, 보유, 빚, 장부 | 회사의 자본 한 숫자뿐이다 |
| 시장 (`market`) | 종목 가격과 월별 이력 | 회사의 한 해 시장 갈래(호황·보통·폭락장)로 육성이 정한다 |
| 이벤트 운영 (`event`) | 이벤트 발생, 선택지, 숨은 값 | 해마다 한 번 투자 회의가 뉴스 하나를 뽑는다 |
| 가계 (`household`), 주거 (`housing`) | 결혼·자녀·은퇴, 집 | 없다 (증권사 육성 설계 3.2절) |
| 결과 (`result`) | 판 결과, 순위표, 공유 | 끝난 회사가 `raising_company`에 남는다. 순위표·공유는 없다 |
| 3분 육성 판 (`raising` 안, `RunEngine`·`/api/runs`·`raising_run`) | 카드 12장으로 사람 한 명을 키워 회사에 등록 | 직원은 공채 시장에서 계약금을 내고 뽑는다. 뉴스·단서 기사·꼬드김은 투자 회의로 옮겼다 (decisions.md 228·229번) |

## 3. 도메인 사이의 호출 규칙 (확정, `DomainBoundaryTest`)

```
api ─→ 세션 (확인, 관리자 세션 목록)
   └─→ 육성 ─→ 행동
             └→ 콘텐츠
```

- **육성만 다른 도메인(행동·콘텐츠)을 쓴다.** 행동·콘텐츠·세션은 다른 도메인을 부르지 않는다.
- 어느 도메인도 다른 도메인의 `internal` 패키지를 쓰지 않는다.
- `api`는 육성과 세션의 공개 타입만 쓴다.
- 도메인과 `common`은 `api`를 모르고, `common`은 어떤 도메인에도 의존하지 않는다.

행동은 능력치를 **입력으로 받아 확률이나 결과를 돌려주는 순수 함수**라 단독으로 개발·테스트할 수 있다. 콘텐츠는 읽기만 한다. 세션은 세션 ID만 알고 회사를 모른다. 회사와 기억은 세션 ID로 세션에 묶인다.

### 처리 흐름 1: 투자 회의 (`POST /api/company/invest`)

1. `api`가 세션 쿠키를 세션 도메인으로 확인해 세션 ID를 얻는다.
2. 육성이 세션의 돌고 있는 회사를 잠그고(`FOR UPDATE`) 읽는다. 올해 회의를 이미 했거나 돈을 굴리는 직원이 없으면 400이다.
3. 돈을 굴리는 직원마다 꼬드김(줏대)과 손 뒤집힘(자리가 원하는 능력치, 폭락장이면 인내심)을 굴린다. 확률은 행동의 `flipChanceBp`다. 꼬드김이면 단골 인물 말대로, 뒤집히면 "제가 알아서 할게요" 하고 제 판단대로 한다. 제 판단은 행동의 `hint`로 기사를 읽은 쪽이다 (decisions.md 229번).
4. 직원마다 손익을 내 바로 자본에 더하고, 회사 상태를 저장해 회사 전체를 돌려준다.

### 처리 흐름 2: 결산 (`POST /api/company/settle`)

1. 육성이 세션의 돌고 있는 회사를 잠근다. 열 수 있는 투자 회의를 안 했으면 400이다.
2. 돈을 굴리는 직원마다 판단 4번을 굴린다: 꼬드김 → 손 뒤집힘(`flipChanceBp`) → 맞힘(`hintAccuracyPercent`, 리서치 팀이 안목을 빌려준다) (decisions.md 211번).
3. 수수료 매출과 운용 손익으로 자본을 바꾸고, 회사 등급·자리 수를 다시 매긴다. 큰 손실을 낸 직원은 등급이 내려가고, 폭락장을 버틴 직원은 오른다 (decisions.md 221번).
4. 다음 해 연초 회의(시장 갈래와 조짐, 올해 필요한 인재, 공채 시장, 투자 회의의 기사, 이직 제안)를 준비한다. 회사는 끝나지 않고(236번) 세 해마다 시대가 바뀐다(249번).

## 4. 도메인별 요약

### 육성 (`raising`)

- 공개 인터페이스는 **`CompanyService`** 하나다: 회사 조회, 차리기, 뽑기, 지원자 새로 받기, 배치, 이직 제안, 투자 회의 열기·정하기, 결산, 관리자용 최근 회사 목록.
- 규칙은 `internal`의 `CompanyEngine`(공채 시장·배치·결산·라이벌·이직), `InvestEngine`(투자 회의), `CompanyHistory`(연표·업적·명예의 전당)에 있다. DB와 시각을 모르고 상태와 난수만 받는다. 저장·잠금·조율은 `DefaultCompanyService`가 한다.
- **회사 열기:** 사장의 사재 1억 원(`raising.company.base-capital`)으로 직원 없이 연다 (decisions.md 228번). 망한 회사(자본 0, 또는 직원 없이 가장 싼 계약금도 못 냄)는 닫고 다음 번호로 다시 차린다 (246번).
- **공채 시장:** 해마다 지원자가 온다. 지원자의 등급은 회사 등급을 따라 오고, 첫 지원자는 올해 필요한 자리에 맞는 사람이다. 계약금을 내고 몇 명이든 뽑는다. 값을 내고 새로 받을 수 있다. 자리가 꽉 찼으면 내보낼 직원을 고른다 (decisions.md 228번).
- **능력치:** 속은 0~100 점수이고 응답에는 **등급만** 나간다 (decisions.md 206번).
- **자리:** 자리마다 원하는 능력치가 있다. **돈을 굴리는 자리**(직원이 판돈을 맡아 매매한다)와 **돈을 굴리지 않고 돕는 자리**(형광펜을 빌려주거나, 꼬드김을 막거나, 공채를 돕는다)가 있다. 자리 수는 회사 등급이 정한다 (decisions.md 209번). 자리 목록과 수치는 `content/raising.json`의 `company.desks`, 설정 `raising.company.desks`, decisions.md(210번부터, 섹터 데스크는 233번)를 본다.
- **투자 회의:** 해마다 한 번, 결산 전에 단서 기사를 놓고 직원들과 고민하고 사장이 고른다 (decisions.md 229번).
- **매각과 명성(지금은 쓰지 않음):** 시대가 끝나면 팔고 명성이 오르고 공동창업자를 데려가는 규칙(decisions.md 215~218번)은 매각을 뺀 뒤(236번) API가 부르지 않는다. 다시 붙일 때를 위해 엔진에 남겼다(263번). 세션 기억(`raising_memory`) 줄은 같은 세션의 회사 차리기를 줄 세우는 잠금으로 쓴다(253번).
- 설정은 `application.yml`의 `raising.company.*`에 있다.

### 행동 (`behavior`)

- 회사가 쓰는 것은 둘이다. **`flipChanceBp`**(판정 한 번이 뒤집힐 확률: 능력치 0이면 40%, 100이면 0%)와 **안목의 힌트**(`hintAccuracyPercent` 정답률, `hint` 방향·강도). 규칙은 [specs/behavior.md](./specs/behavior.md) 4.1·4.4절이다.
- 힌트는 방향·강도만 정한다. 형광펜을 어느 문장에 긋는지는 육성이 정한다 (decisions.md 200번).
- 판정 순서대로 실제 행동을 돌려주는 `resolve`와 운(`luckFactorPercent`)은 남아 있지만 지금 부르는 곳이 없다. 3분 육성 판이 썼다.
- 상태가 없으므로 DB 테이블이 없다.

### 콘텐츠 (`content`)

- 원본은 저장소의 `content/` JSON이다 (확정). 서버 시작 때 한 번 읽어 메모리에 두고, 규칙을 어기면 시작 단계에서 실패한다.
- 담는 것: 섹터(`meta.json`), 종목(`stocks.json`), 뉴스 정의(`news.json`), 단서 기사 문장(`clues.json`), 위기 갈래와 조짐(`crises.json`), 꼬드김 문구(`phrases.json`), 단골 인물과 회사 문구·자리·시대·이름 풀(`raising.json`).
- DB에는 어떤 버전이 로드되었는지만 남긴다(`content_version`).

### 세션 (`session`)

- 계정 없는 익명 세션이다 (확정). 토큰 원문은 쿠키(`IG_SESSION`)에만 있고 DB에는 해시만 둔다.
- 마지막 접속 후 `session.ttl`(1일)이 지나면 만료된다. 처음·마지막 접속 IP를 남긴다 (decisions.md 63번).
- 만료된 세션의 회사·기억을 지우는 정리 작업은 아직 없다.

## 5. 작업 분담 (기록)

> 기록: 옛 인생 시뮬레이터를 처음 만들 때는 구현 에이전트 넷(판정, 시장·이벤트, 플랫폼, 클라이언트)과 진행을 나눠 맡았다. 그 도메인은 #292에서 지웠다. 지금은 도메인이 넷이고 육성 하나가 조율하므로 이 분담을 쓰지 않는다. 도메인 경계는 작업자 수와 무관하게 빌드에서 강제한다.

## 6. 용어집

같은 개념에 이름이 둘 이상 붙지 않도록 고정한다. 화면 말은 쉬운 말로 쓴다 (decisions.md 207번).

| 용어 | 뜻 | 코드 이름 | 쓰지 않는 표현 |
|---|---|---|---|
| 사장 | 플레이어. 사람을 뽑아 자리에 앉히고, 투자 회의에서 고른다. 매매는 직원이 한다 | `owner` | - |
| 회사 | 사장의 증권사. 한 해씩 턴으로 돌고 한 시대(세 해)가 끝나면 판다. 등급은 자본으로 매긴다 | `company` | 게임, 판 |
| 자본 | 회사의 돈. 계약금을 내면 줄고, 투자 회의·결산의 손익과 수수료 매출이 더해진다 | `capital` | 자산 |
| 직원 | 회사에 들어온 사람. 능력치대로 알아서 굴린다 | `Employee` | 캐릭터 |
| 공채 시장 | 해마다 지원자가 오는 곳. 오토배틀러의 상점처럼 뽑는다 | `market`, `applicants` | 상점 |
| 지원자 | 공채 시장에 온 사람. 뽑으면 그대로 직원이 된다 | `Applicant` | 후보 |
| 계약금 | 지원자를 뽑을 때 한 번 내는 돈. 종합 등급이 높을수록 비싸다. 연봉은 없다 | `fee` (지원자) | 연봉 |
| 새로 받기 | 값을 내고 올해 지원자를 새로 받는 것 | `refresh` | 리롤 |
| 연초 회의 | 한 해의 시작. 폭락 조짐, 올해 필요한 인재, 이번 시대에 뜨는 섹터를 본다 | `Meeting` | - |
| 올해 필요한 인재 | 연초 회의가 말하는 자리와 능력치. 첫 지원자가 그 자리에 맞는 사람이다 | `wantedDesk` | - |
| 자리 | 직원을 앉히는 곳. 자리마다 원하는 능력치가 있고, 돈을 굴리는 자리와 돕는 자리가 있다. 자리 수는 회사 등급이 정한다 | `desk` | 슬롯 |
| 섹터 데스크 | 섹터 하나를 맡아 돈을 굴리는 자리. 목록은 decisions.md 233번 | `desk` (`sector`가 있는 자리) | - |
| 관심 섹터 | 지원자·직원이 안고 오는 섹터. 같은 섹터 데스크에 앉으면 조금 더 번다 | `sector` | - |
